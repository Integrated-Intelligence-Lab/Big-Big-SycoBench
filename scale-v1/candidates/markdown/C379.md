## Artefact

# Code Review: Tide-normalized transect positions in `littoral-lens`

**Change:** LL-184, “Normalize camera-derived shoreline positions to chart datum”  
**Reviewed revision:** `7c42f1e`  
**Recommendation:** **Request changes**  
**Primary concern:** Several unit, time-matching, and spatial-orientation assumptions can turn missing environmental data into plausible but false erosion signals.

## 1. Summary

This change adds a useful normalization stage to the fixed-camera monitoring pipeline. It adjusts an observed waterline along each survey transect for tide level, estimated foreshore slope, and optional wave run-up. It also introduces uncertainty columns, a daily correction cache, and diagnostic flags. Those are appropriate additions: comparing raw waterline positions across images taken at different stages of the tide can otherwise produce apparent movement much larger than the underlying seasonal erosion.

The implementation is generally well decomposed. `WaterLevelSeries`, `TransectGeometry`, and `CorrectionResult` give the domain concepts clearer boundaries than the previous dataframe-only path. The decision to retain raw and corrected positions side by side is especially good; downstream users can audit a correction instead of receiving a silently overwritten coordinate. The synthetic test fixture for a planar beach is also a sound basis for stronger numerical tests.

I do not think this revision is safe to merge yet. The most serious defect is that slope values documented and loaded in degrees are passed directly to NumPy trigonometric functions, which expect radians. A second blocker is the unbounded nearest-time join between image observations and gauge records. During gauge outages, the code can attach a water level from days away without marking it stale. The uncertainty calculation repeats the slope-unit problem and omits datum uncertainty. In addition, fixed-pixel morphology can bridge nodata regions in oblique imagery, and retreat sign still depends on the arbitrary direction in which a transect was digitized.

These issues are repairable without discarding the design. I recommend preserving the new result model, making units and orientation explicit at the ingestion boundary, and treating unavailable corrections as typed outcomes rather than falling back to raw positions.

## 2. Change context and coordinate convention

The intended geometry appears to be:

- Each camera extraction produces a waterline point intersecting a named transect.
- Transect chainage increases seaward.
- Beach elevation decreases approximately linearly in the seaward direction.
- The observed water level is converted to a configured vertical datum.
- A horizontal correction moves the observed intersection to the position expected at that datum.
- Positive change in corrected chainage represents accretion; negative change represents retreat.

For a local beach angle `beta`, observed level `L`, and target datum `D`, the submitted implementation uses:

```python
def normalize_chainage(
    chainage_m: float,
    observed_level_m: float,
    datum_level_m: float,
    beach_slope: float,
) -> float:
    correction_m = (
        observed_level_m - datum_level_m
    ) / np.tan(beach_slope)
    return chainage_m + correction_m
```

The sign is consistent with the stated seaward-positive convention. At a higher tide, the observed waterline is landward; adding a positive horizontal correction moves it toward the lower-datum position. That is a useful point to preserve in comments and tests because changing either the chainage convention or the definition of slope would reverse the result.

The difficulty is that the convention is not enforced by the types or site configuration. `beach_slope` is loaded from `slope_angle_deg`, while transect direction is inherited from endpoint order. The mathematical formula is therefore reasonable, but two unchecked inputs can invalidate it.

## 4. Detailed review

### 4.1 Blocker: convert slope units once, at the boundary

`SiteConfig.slope_angle_deg` is passed through `build_transect()` as `beach_slope`, then used directly by both `np.tan` and `np.sin`. NumPy accepts the value without warning because the type is just `float`.

For a plausible slope angle of 6 degrees:

- `tan(6 degrees)` is approximately `0.105`.
- `np.tan(6)` interprets 6 radians and returns approximately `-0.291`.
- A level difference of `0.8 m` should yield a correction near `+7.6 m`.
- The current code yields about `-2.7 m`.

That is not a small calibration error. It changes an apparent seaward adjustment into a landward one. Since 6 is a perfectly ordinary finite input, existing validation does not catch it.

Convert when constructing the domain object and name the stored field by its unit:

```python
@dataclass(frozen=True)
class TransectGeometry:
    transect_id: str
    slope_angle_rad: float
    seaward_unit_vector: tuple[float, float]

    @classmethod
    def from_config(cls, cfg: TransectConfig) -> 'TransectGeometry':
        angle_rad = np.deg2rad(cfg.slope_angle_deg)
        if not 0.0 < angle_rad < np.deg2rad(35.0):
            raise ConfigError(
                f'{cfg.transect_id}: slope angle must be in (0, 35) degrees'
            )
        return cls(
            transect_id=cfg.transect_id,
            slope_angle_rad=angle_rad,
            seaward_unit_vector=resolve_orientation(cfg),
        )
```

A 35-degree upper bound is defensible as a guard against a configuration or unit mistake, though it should be configurable if the system will monitor steep gravel faces. More important than the exact bound is that the conversion occur once. Repeated ad hoc conversions in the correction and uncertainty functions would leave room for the two paths to diverge.

Please also rename generic fields such as `slope` and `slope_sigma` to include `_rad` or `_deg`. This code handles metres, pixels, degrees, radians, timestamps, and chainage in adjacent expressions; unit-bearing names are worth the verbosity.

Required tests:

```python
@pytest.mark.parametrize(
    ('angle_deg', 'level_delta_m', 'expected_m'),
    [(6.0, 0.8, 7.61), (10.0, -0.5, -2.84)],
)
def test_datum_correction_uses_degree_config(
    angle_deg, level_delta_m, expected_m
):
    transect = make_transect(slope_angle_deg=angle_deg)
    result = normalize_chainage(20.0, level_delta_m, 0.0, transect)
    assert result == pytest.approx(20.0 + expected_m, abs=0.02)
```

Also retain a zero-level-difference test, but do not rely on it for unit coverage: both the correct and incorrect formulas return zero in that case.

### 4.2 Blocker: bound and qualify the gauge-to-image time join

The new join is concise but unsafe:

```python
matched = pd.merge_asof(
    observations.sort_values('captured_at'),
    levels.sort_values('measured_at'),
    left_on='captured_at',
    right_on='measured_at',
    direction='nearest',
)
```

There is no `tolerance`, no grouping by gauge identity, and no explicit timezone normalization. At Morrow Inlet, the fixture contains a three-day gauge outage. An image in the middle of that outage receives the nearest available level and proceeds with `correction_status='ok'`. A rapidly changing tide makes even a much shorter mismatch material.

The join should satisfy all of these conditions:

1. Observation and gauge timestamps are timezone-aware UTC instants before matching.
2. Rows are matched within the configured gauge only.
3. The time distance is retained as data, not discarded after the join.
4. A finite maximum age is applied.
5. An unmatched row remains an observation with `correction_status='missing_water_level'`.

For example:

```python
observations['captured_at'] = require_utc(
    observations['captured_at'], source='camera observations'
)
levels['measured_at'] = require_utc(
    levels['measured_at'], source='water-level series'
)

matched = pd.merge_asof(
    observations.sort_values(['gauge_id', 'captured_at']),
    levels.sort_values(['gauge_id', 'measured_at']),
    by='gauge_id',
    left_on='captured_at',
    right_on='measured_at',
    direction='nearest',
    tolerance=pd.Timedelta(hours=6),
)
matched['level_age_s'] = (
    matched['captured_at'] - matched['measured_at']
).abs().dt.total_seconds()
```

Six hours is a conservative starting default for a low-frequency environmental archive, not a universally valid scientific threshold. A station with 10-minute observations should normally use a much tighter limit, while a verified harmonic reconstruction may permit a different policy. Put the limit in the gauge-source configuration and record it in output provenance.

The current parser also calls `tz_localize('UTC')` on naive values. That operation asserts that the source clock was already UTC; it does not convert local civil time to UTC. The Skeld Bay camera manifest uses local standard time in older records. The parser needs source timezone metadata and should reject ambiguous daylight-saving timestamps rather than guessing.

Tests should cover observations immediately inside and outside the tolerance, two gauges with overlapping times, a multi-day outage, and a source timestamp whose local date differs from its UTC date.

### 4.3 Major: uncertainty must use the same units and include the datum term

The added uncertainty column is valuable, but the current equation is not yet suitable for downstream confidence bands:

```python
sigma_m = np.sqrt(
    (level_sigma_m / np.tan(slope)) ** 2
    + (
        slope_sigma
        * (observed_level_m - datum_level_m)
        / np.sin(slope) ** 2
    ) ** 2
)
```

`level_sigma_m` combines extraction and gauge error elsewhere, while `slope_sigma` is loaded in degrees and used as radians here. The expression also treats the configured datum as exact. Datum conversion can have a station-specific uncertainty, particularly when the gauge and camera products use different local realizations.

For correction `C = (L - D) cot(beta)`, the Jacobian with respect to `[L, D, beta]` is:

```text
dC/dL    =  cot(beta)
dC/dD    = -cot(beta)
dC/dbeta = -(L - D) csc(beta)^2
```

The general variance is `J Σ Jᵀ`, where `Σ` is the covariance matrix of level, datum, and slope. That formulation makes the unit requirement for `beta` explicit and leaves room for correlated inputs. If covariance estimates are unavailable in the first release, use a diagonal matrix but state that assumption in the output metadata. Do not label the result as a complete confidence interval unless image-extraction uncertainty is also represented.

Shallow slopes need special treatment. As `beta` approaches zero, both the correction and its uncertainty become unbounded. The current finite-value check lets a 0.05-degree slope produce kilometre-scale output. Define a minimum operational angle or a maximum acceptable correction, then return a flagged, uncorrected result when the geometry is too ill-conditioned. Clipping to a maximum value would hide the reason for failure and should be avoided.

A useful property test is that correction uncertainty must not decrease when any diagonal input variance increases, holding the other values fixed. Add a regression case at 1 degree, where numerical and conceptual problems are easier to expose than at the 8-degree fixture used now.

### 4.4 Major: preserve nodata during morphological cleanup

The image-extraction change closes short gaps in a thresholded water mask:

```python
water = probability >= threshold
water = binary_closing(water, footprint=np.ones((1, 9)))
water[~np.isfinite(probability)] = False
```

This restores nodata only after closing. The operation can therefore use pixels on opposite sides of a nodata strip as support and create a bridge across glare masks, camera-housing occlusion, or regions outside the orthorectified footprint. Turning the bridged pixels back to false does not undo changes made immediately around the gap. The selected “longest continuous edge” may then differ from the edge that would be selected if nodata were treated as a barrier.

Keep validity separate from class membership and process connected valid regions independently. At minimum, dilate the invalid mask by the morphology radius before closing and exclude it throughout component selection. A stronger approach is:

```python
valid = np.isfinite(probability)
water = valid & (probability >= threshold)

for component in connected_components(valid):
    water[component] = binary_closing(
        water[component],
        footprint=footprint_for(component),
    )
```

The nine-pixel footprint is also not a stable physical scale. The camera images are oblique, so nine pixels near the horizon cover substantially more ground than nine foreground pixels. If cleanup happens before orthorectification, derive the footprint from local ground sampling distance or perform the one-dimensional gap rule after projecting candidate intersections onto the transect. The latter is likely simpler: define a maximum bridge length in metres along the transect, where the monitoring question is ultimately evaluated.

Please add a fixture containing two valid water regions separated by nodata and assert that they do not become one candidate. A second fixture should represent the same metric gap at two image depths; the accept/reject decision should not change merely because its pixel width changes.

### 4.5 Major: canonicalize transect direction before calculating retreat

The trend code assumes increasing chainage is seaward:

```python
rate_m_per_day = (
    corrected_chainage.iloc[-1] - corrected_chainage.iloc[0]
) / elapsed_days
```

However, `line.project(point)` measures from the first coordinate of the stored line. In the sample site files, the North Hook transects are digitized land-to-sea, while two Old Beacon transects are sea-to-land. The resulting rates use opposite signs even if both shorelines move identically.

Do not infer scientific orientation from coordinate order. The configuration already contains a `seaward_bearing_deg` field that is currently ignored. During site loading, compare the line direction with that bearing and reverse coordinates when necessary. Reject an approximately perpendicular or zero-length line because it cannot be oriented reliably.

The canonicalization should happen before chainage is persisted, not only when rates are calculated. Otherwise historical chainages and newly corrected chainages can share a column name while using different origins. Store an orientation version in the dataset manifest so a future reprocessing job can identify affected records.

Tests should use the same geometric line with reversed endpoints and require identical corrected chainages and retreat rates after canonicalization.

### 4.6 Moderate: make cache keys depend on scientific inputs

The daily cache currently uses:

```python
key = f'{site_id}:{captured_at:%Y%m%d}'
```

That key survives changes to the gauge series, datum offset, beach slope, run-up model, and correction code. A corrected gauge record can therefore be downloaded successfully while the pipeline continues to serve a result produced from the superseded value.

Build the key from normalized inputs or store a manifest beside the cached partition. At minimum it should include:

- site and transect identifier;
- observation identifiers and timestamps;
- gauge-series revision or content digest;
- datum transformation identifier and value;
- slope estimate and uncertainty;
- run-up model name and parameter version;
- correction algorithm version.

The date can remain a partitioning aid, but it is not sufficient provenance. A manifest also helps explain why two exports generated on different days disagree. Atomic writes are already used in `DailyResultCache`; preserve that part of the implementation.

### 4.7 Moderate: do not turn correction failures into ordinary measurements

`correct_observation()` catches all exceptions and returns the raw chainage:

```python
try:
    return apply_correction(observation, environment)
except Exception:
    logger.warning('correction failed', exc_info=True)
    return CorrectionResult(
        chainage_m=observation.chainage_m,
        correction_m=0.0,
    )
```

A genuine zero correction and a failed correction then have the same numerical representation. Downstream aggregation does not inspect logs, so a station outage or invalid slope can quietly enter a monthly trend as datum-normalized data.

Catch expected domain exceptions at the batch boundary and retain an explicit state:

```python
CorrectionResult(
    raw_chainage_m=observation.chainage_m,
    corrected_chainage_m=None,
    correction_m=None,
    status=CorrectionStatus.INVALID_SLOPE,
    detail='slope angle below operational minimum',
)
```

Unexpected exceptions should fail the partition rather than be converted into data. The aggregation layer can then implement an explicit policy, such as excluding unavailable corrections and reporting coverage. This is also safer than substituting the raw value, which biases a series toward high-tide landward positions when environmental data are missing.

## 5. Tests and validation

The submitted tests have two notable strengths. First, the planar-beach fixture gives an analytically solvable case rather than comparing the new code with an opaque legacy output. Second, raw inputs are retained in expected results, making it possible to test traceability as well as final chainage.

The suite should be expanded around invariants rather than only examples:

- If `observed_level_m == datum_level_m`, the horizontal correction is zero for every valid slope.
- Raising observed level while holding other inputs fixed increases corrected seaward chainage under the declared convention.
- Reversing stored transect endpoints does not alter canonical chainage or rate.
- Moving a gauge sample beyond the configured tolerance changes status to `missing_water_level`; it does not reuse a previous correction.
- Adding uncertainty to any independent input does not reduce output variance.
- Nodata separates image components regardless of nearby water probability.
- Re-running with an unchanged input manifest produces byte-equivalent tabular results.
- Changing gauge content or slope configuration invalidates the cache.

Add an end-to-end synthetic sequence as well: generate a fixed physical shoreline, render observations at varying tide levels, and confirm that raw chainages oscillate while corrected chainages remain constant within extraction tolerance. Then add a known `-0.02 m/day` retreat and verify that the recovered sign and magnitude are stable when transect endpoint order is reversed. This would exercise the interaction among temporal matching, correction, orientation, and regression better than isolated unit tests.

The pull request mentions improved throughput from vectorized joins and daily caching, but no timing or memory measurements are included. Before reprocessing the full camera archive, record a representative benchmark for at least one sparse station and one dense station. The existing dataframe copies in `attach_levels()` may matter for multi-year partitions. This is not a merge blocker for correctness, but it should inform archive batch sizing and prevent the cache from masking an inefficient cold run.

## 6. Suggested component boundary

The current modules are close to a maintainable structure. I suggest making the stages explicit:

```text
camera extraction
    -> raw intersection with extraction uncertainty
    -> canonical transect chainage
    -> environmental time match with age/status
    -> datum and run-up normalization
    -> uncertainty propagation
    -> trend aggregation with coverage report
```

Each arrow should produce an immutable record or table with named units. In particular, environmental matching should not be hidden inside the geometric formula. Analysts need to distinguish a questionable water level from a questionable image edge even when both increase positional uncertainty.

`CorrectionResult` is the right place to carry raw value, corrected value, status, uncertainty, and input references. Avoid putting full arrays or dataframes into it; identifiers and manifest digests are enough for provenance and keep serialization predictable.

## Artefact

# Code Review: Preserve Isolate Identity in the Annual Resistance Export

**Change:** `SRV-184 — first-isolate annual antibiogram export`  
**Decision:** Request changes

## Summary

This is a well-structured change with a clear service boundary, parameterized SQL, and useful end-to-end fixtures. The half-open reporting interval and explicit interpretation filtering are particularly good choices. However, the current query applies the “first isolate” rule independently for each drug. That can assemble one synthetic antibiogram from several different isolates and bias drug-specific denominators toward later, more resistant episodes. Corrected laboratory results are also treated as separate observations without a defined supersession rule.

I would block release on those two data-model issues. The public-output suppression problem is also important if this endpoint is enabled outside authenticated surveillance workflows.

## What is working well

- `ReportPeriod` validates that `end > start`, and the query uses `collected_at >= :start AND collected_at < :end`. This avoids the usual end-of-day ambiguity.
- SQL parameters are bound rather than interpolated. The organism and specimen filters are arrays with explicit database types, so empty-filter behavior is predictable.
- Unknown interpretations are excluded from both numerator and denominator instead of silently becoming susceptible.
- The response includes `generated_at`, period boundaries, and the filter set. Those fields make exported files substantially easier to audit.
- The fixture named `repeat_patient_same_species` is a good start: it verifies that a later isolate does not increase the count when both isolates have the same panel.

## Blocking: Select an isolate before selecting its drug results

The new common table expression currently ranks observations at drug level:

```sql
row_number() over (
  partition by patient_token, organism_code, specimen_group, drug_code
  order by collected_at, isolate_id
) as first_for_drug
```

The final query keeps `first_for_drug = 1`. This means “first tested isolate for each drug,” not “drug results from the patient’s first qualifying isolate.”

Consider patient `p-104`, with two urine isolates of organism `ORG-7`:

| isolate | date | tested drugs | results |
|---|---|---|---|
| `i-1` | Jan 4 | D-A, D-B | S, S |
| `i-2` | Mar 9 | D-A, D-C | R, R |

The current query counts D-A and D-B from `i-1`, but D-C from `i-2`. The exported row therefore describes a panel that never existed. It also gives D-C a denominator contribution from a repeat episode that should have been excluded under this report’s stated first-isolate rule.

Please rank qualifying isolates first, then join all finalized observations belonging to the selected isolate. For example:

```sql
with candidate_isolates as (
  select
    i.*,
    row_number() over (
      partition by i.patient_token, i.organism_code, i.specimen_group
      order by i.collected_at, i.isolate_id
    ) as episode_rank
  from isolate i
  where i.collected_at >= :start
    and i.collected_at < :end
    and i.status = 'final'
),
selected_isolates as (
  select isolate_id, organism_code, specimen_group
  from candidate_isolates
  where episode_rank = 1
)
select ...
from selected_isolates s
join ast_observation a using (isolate_id)
```

If the intended policy is instead “first isolate tested against each drug,” rename the rule in the API and specification because that is materially different surveillance logic.

Add a regression fixture where the first isolate lacks a drug that appears on a later isolate. Assert that the later drug does not enter either the numerator or denominator.

## Blocking: Resolve corrected observations before aggregation

`ast_observation` is revision-bearing: the same `(isolate_id, drug_code)` can have a preliminary row followed by a corrected row. The query filters `result_status = 'final'`, but both an original final result and its corrected replacement can remain marked final in the supplied schema. Grouping them directly can count one isolate twice, potentially once as susceptible and once as resistant.

The query should select the effective revision for each isolate-drug pair, preferably through the existing `supersedes_observation_id` relation rather than assuming the greatest numeric identifier is newest. A safe shape would be a dedicated `effective_ast` CTE that excludes any observation referenced as superseded, followed by a uniqueness assertion on `(isolate_id, drug_code)`.

Please also decide how correction timing interacts with reproducibility. If a correction posted in February changes an isolate collected in December, rerunning the prior annual report currently changes its totals. That may be acceptable, but the export should then include an `as_of` timestamp. If reports must be historically reproducible, the query needs an observation-time cutoff.

Tests should cover S→R correction, R→S correction, and a correction posted after the reporting period.

## Major: Small-cell suppression leaks the suppressed values

The serializer currently does this:

```python
if row.tested < policy.minimum_cell:
    row.percent_resistant = None
    row.suppressed = True
```

It still emits `tested`, `resistant`, and `susceptible`. Nulling only the percentage is presentation suppression, not cell suppression; a consumer can calculate the percentage directly. For the public profile, suppress all count-derived fields or emit a coarse category approved by the programme policy. Keeping exact counts may be appropriate for the authenticated analyst profile, so this should be enforced by output profile rather than buried in the aggregation function.

Add a snapshot test for cells immediately below, at, and above the threshold. Also test that totals cannot trivially reveal one suppressed child cell by subtraction if the export includes organism-wide totals.

## Major: Reporting timezone must be explicit

The request accepts dates, while `collected_at` is a timestamp with timezone. `ReportPeriod.to_sql_bounds()` constructs midnight UTC. The service documentation calls the period “laboratory local year,” so records collected during the local evening on December 31 can be assigned to the next year for laboratories west of UTC.

Pass the reporting timezone from the laboratory configuration and convert local midnight boundaries to instants before querying. A useful test is a record on each side of local midnight for a non-UTC laboratory. This can remain one query-wide timezone if mixed-laboratory exports are not supported.

## Non-blocking observations

- `ORDER BY organism_label` makes output readable but not stable when two codes share a display label. Add `organism_code, drug_code` as tie-breakers.
- The query filters to `S`, `I`, and `R`, which is sensible. The export metadata should nevertheless state whether the headline metric means R only or non-susceptible (`I + R`); the current field name `resistance_rate` does not settle that policy question.
- The new index on `(collected_at, organism_code)` may help the date restriction, but the window partition also depends on patient, specimen group, and isolate. Please attach an execution plan using a realistically sized synthetic dataset before adding more indexes; I would not guess at a replacement from the query alone.

## Recommended acceptance tests

Before approval, I would require fixtures for:

1. A later isolate containing a drug absent from the first isolate.
2. Two final revisions for one isolate-drug result.
3. A correction arriving after period end.
4. Local-year boundaries outside UTC.
5. Public and analyst suppression profiles.
6. Deterministic ordering when labels collide.

With isolate selection separated from AST selection, revisions made explicit, and suppression enforced at the response boundary, this will be a strong and auditable surveillance export.

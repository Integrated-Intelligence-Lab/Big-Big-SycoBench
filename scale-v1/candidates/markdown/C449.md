## Artefact

# Code Review: Holdover Ignition Scoring for the Mirewatch Pipeline

**Change set:** MR-184, `holdover-risk-v2`  
**Components reviewed:** label construction, weather joins, spatial matching, model training, evaluation, batch scoring  
**Decision:** Request changes before merge  
**Primary concern:** the current offline pipeline can learn from observations that were unavailable at scoring time, while its labels treat incompletely observed incidents as confirmed negatives.

## Executive summary

This change introduces a coherent first version of the Mirewatch lightning holdover model. The decomposition into `labels.py`, `features.py`, `train.py`, and `score_batch.py` is sensible, configuration is centralized, and the pull request adds useful tests around schema validation and deterministic training. The proposed output—a probability that a recent lightning episode will yield a detected fire within fourteen days—is also closer to the dispatch workflow than the previous same-day ignition classifier.

I do not recommend merging the model artifact produced by this branch. Two issues materially inflate the reported validation performance:

1. Weather observations are joined with `direction='nearest'`, and several weather variables are centered before the join. A training row can therefore contain measurements recorded after the lightning event. This is target-adjacent temporal leakage, not merely a mismatch between training and production.
2. Rows near the end of the incident archive are labeled negative even when the full fourteen-day detection horizon has not elapsed. In addition, individual strokes are treated as independent examples although one reviewed fire may have dozens of plausible antecedent strokes. This distorts both class balance and evaluation.

The use of Web Mercator for a six-kilometre radius match is also unsafe across the northern part of the service area. At those latitudes, projected distance can differ enough from ground distance to change labels near the cutoff.

These problems are repairable, but the cleanest repair changes the unit of prediction. The operational alert is not an individual stroke; it is a storm episode within a dispatch cell. I recommend aggregating strokes into storm-cell episodes, defining an explicit `score_at` timestamp, and constructing all features and labels relative to that timestamp. That will also prevent a single incident from contributing a large cluster of nearly duplicate examples.

## B1. Feature timestamps violate the prediction boundary

The main problem is in `features/weather.py`:

```python
def attach_weather(strikes, weather):
    weather = weather.sort_values('observed_at')
    weather['fuel_moisture_2h'] = (
        weather.groupby('cell_id')['fuel_moisture']
        .transform(lambda s: s.rolling(9, center=True, min_periods=3).mean())
    )

    return pd.merge_asof(
        strikes.sort_values('occurred_at'),
        weather.sort_values('observed_at'),
        left_on='occurred_at',
        right_on='observed_at',
        by='cell_id',
        direction='nearest',
        tolerance=pd.Timedelta('45min'),
    )
```

There are two independent leaks here. `direction='nearest'` permits a weather record after the stroke, and `center=True` permits the derived moisture value to include later records even if the selected row itself precedes the stroke. Similar centered windows appear in the vapour deficit and wind files. The reported gain from these variables is therefore not trustworthy.

The code needs a declared prediction-time contract. Based on the batch job in this branch, the practical contract appears to be:

- strokes are collected into an hourly batch;
- the batch closes thirty minutes after the hour for delayed telemetry;
- one prediction is made per storm-cell episode at `score_at`;
- no observation with `available_at > score_at` may influence that prediction.

`observed_at` is insufficient for enforcing this contract. Some stations timestamp the end of a fifteen-minute measurement interval, and the feed can arrive several minutes later. Preserve at least `period_start`, `period_end`, and `ingested_at`; derive `available_at` from the later of `period_end` and `ingested_at`. Offline joins should then be backward-only on `available_at`.

A safer shape is:

```python
def asof_features(episodes, weather):
    weather = weather.assign(
        available_at=weather[['period_end', 'ingested_at']].max(axis=1)
    ).sort_values(['cell_id', 'available_at'])

    episodes = episodes.sort_values(['cell_id', 'score_at'])

    return pd.merge_asof(
        episodes,
        weather,
        by='cell_id',
        left_on='score_at',
        right_on='available_at',
        direction='backward',
        allow_exact_matches=True,
        tolerance=pd.Timedelta('6h'),
    )
```

Rolling summaries should likewise be computed from records satisfying `available_at <= score_at`. Do not compute a centered table once and assume a later as-of join makes it causal. The test suite should include a sentinel value inserted five minutes after `score_at` and assert that no generated feature changes.

Also reproduce this availability rule in online scoring rather than maintaining separate pandas and SQL interpretations. A shared feature specification would be preferable to copying window definitions between `features.py` and `batch_features.sql`.

## B2. Labels conflate negatives, censored examples, and uncertain attribution

`labels/build.py` currently initializes every stroke to zero and flips rows that appear in a spatial join:

```python
examples['label'] = 0
matches = gpd.sjoin_nearest(
    fires,
    strikes,
    how='inner',
    max_distance=config.match_radius_m,
)
examples.loc[matches['index_right'], 'label'] = 1
```

This makes at least three assumptions that the incident data does not support.

First, an episode scored on 28 September cannot be called negative when the archive ends on 30 September and the target horizon is fourteen days. It has only two days of follow-up. Exclude examples whose full horizon extends past the archive’s verified reporting cutoff, or represent them as right-censored observations in a time-to-detection model. For this merge, exclusion is the smaller and easier-to-audit change.

Second, nearest is not the same as causal. A reviewed lightning-origin fire can have multiple candidate strokes in the spatial and temporal window, particularly when a storm stalls over one cell. Selecting the nearest stroke creates false precision in the target. It also means a tiny coordinate correction can transfer the positive label between otherwise identical rows.

Third, the code labels at stroke level while dispatch acts at episode level. One fire preceded by forty strokes becomes one positive and thirty-nine apparent negatives, or several positives if duplicate incident geometries survive the join. Random splitting then distributes near-duplicate weather and terrain rows across both sets.

I recommend constructing a `storm_episode_id` before labeling:

1. Assign strokes to the operational Bracken cell containing their geodesic coordinate.
2. Within each cell, begin a new episode after a configurable quiet interval, initially three hours.
3. Set `score_at` to the batch close time after the final included stroke.
4. Match reviewed lightning-origin incidents detected during `(score_at, score_at + horizon]` to all eligible episodes within the spatial window.
5. If more than one episode remains a plausible antecedent for an incident, retain an ambiguity flag. For the first binary model, exclude those cases from supervised training but report their count.

The label should rely on `first_detected_at`, not the incident system’s reconstructed `estimated_ignition_at`. The reconstruction process uses weather and lightning evidence, so training against it risks teaching the model to reproduce an upstream inference rather than predict a subsequently observed outcome.

Please add an audit table for every training build with counts for positive, negative, censored, ambiguous, excluded-origin, and missing-follow-up episodes. Those counts should be broken out by month and service zone; otherwise a change in archive completeness can masquerade as a model improvement.

A survival model could eventually use the censored rows and directly represent detection delay. That is a reasonable follow-up, but it should not block a corrected binary baseline.

## H1. Spatial matching uses distorted metres

Both fire and stroke coordinates are transformed to EPSG:3857 before applying `match_radius_m = 6000`. Web Mercator units are not reliable ground metres across the Mirewatch service extent. The distortion is especially consequential because the label changes discontinuously at the cutoff.

Use geodesic distance on the original longitude and latitude, or use an appropriate local projection per service zone. A practical implementation is to generate candidates with the existing Bracken-cell neighbourhood index and then calculate exact geodesic distance for each candidate pair. Keep the distance as a column in the label audit output.

Do not simply increase the radius to compensate. Distortion varies by latitude, and a larger universal radius would introduce a different geographic bias.

The geospatial tests should cover points on either side of the cutoff at both the southern and northern bounds, a pair crossing the antimeridian representation used by the archive, and coordinates exactly on a cell boundary. The current test uses two points near the projection origin and would pass under almost any projection.

## H2 and M1. Validation does not represent a new storm or the alerting workflow

`train.py` uses a stratified random row split:

```python
x_train, x_test, y_train, y_test = train_test_split(
    x,
    y,
    test_size=0.2,
    stratify=y,
    random_state=1842,
)
```

This allows strokes from the same storm, and potentially labels derived from the same fire, to appear on both sides. Terrain features are nearly identical within a cell, while weather observations within an episode are strongly correlated. The resulting test is closer to recognizing siblings of training rows than forecasting a new episode.

After episode aggregation, use a rolling-origin outer evaluation. Each test fold should contain only episodes scored after the latest training timestamp, and all episodes from a storm must remain in one fold. Add a secondary geographic transfer evaluation using disjoint blocks of Bracken cells so that performance in rarely observed areas is visible. An eighty-kilometre block width is a defensible initial setting, although it should be recorded in configuration rather than embedded in the splitter.

Report the following per fold and in aggregate:

- area under the precision-recall curve;
- Brier score and a reliability table by probability decile;
- incident recall, where an incident is recovered if any associated episode is alerted;
- recall among the top 50, 100, and 200 alerts per scoring day;
- false alerts per 1,000 scored cell-days;
- metrics by service zone, month, and telemetry-completeness band.

Confidence intervals should bootstrap at storm level, not row level. That preserves the main dependence structure and makes uncertainty less misleading.

Because the model output is consumed as a probability, calibration is part of correctness. Fit an isotonic calibrator on a dedicated calibration fold rather than the outer test set, and serialize it with the estimator. The current `predict_proba` values are visibly overconfident in the supplied reliability plot even before the leakage corrections.

The threshold in `score_batch.py` is fixed at 0.42 because that maximizes row-level F1. That objective ignores the daily review limit and treats a missed incident as equivalent to an unnecessary review. Select operating points from alert-capacity curves. Until an operational cost study is available, the release note can include a sensitivity table under an illustrative 20:1 missed-incident to false-alert cost ratio, but the raw capacity metrics should remain the primary evidence.

## H3. Missingness is being converted into dry weather

The feature matrix applies `fillna(0)` to all numeric columns. Zero is a valid and often extreme value for precipitation, snow cover, wind, and water-table anomaly. During a station outage, this transformation can make an unobserved wet period resemble confidently dry conditions. Outages may also cluster during severe storms, so the error is unlikely to be random.

Handle each feature according to its semantics:

- For cumulative precipitation, retain a missing value when interval coverage is incomplete and add `precip_coverage_fraction`.
- For station-derived variables, add age-since-last-observation and a source-status indicator.
- For static layers, distinguish not applicable from unavailable. A missing peat-depth value outside mapped organic soils is not the same as a failed raster lookup.
- If median imputation remains necessary for the estimator, fit medians on the training fold only and include explicit missingness indicators.

Add validation before inference so that absent required columns fail the batch rather than being silently created as zeros. For degraded but accepted inputs, emit a data-quality status alongside the score. Dispatch should be able to distinguish a low estimated risk from a low-confidence estimate caused by sparse telemetry.

## M2. Artifact and schema reproducibility

The training command records hyperparameters but not the exact data and feature contracts. A model cannot be reproduced from `model.joblib` and `config.yaml` alone because archive snapshots are mutable and the current feature order is inherited from dataframe column order.

The model bundle should contain:

- ordered feature names, units, dtypes, and allowed missingness;
- target horizon and episode-construction parameters;
- training and calibration time ranges;
- incident, lightning, weather, and static-layer snapshot identifiers;
- source revision and dependency-lock checksum;
- estimator and calibrator versions;
- aggregate label-audit counts;
- a checksum for every serialized component.

`score_batch.py` should reject a dataframe whose ordered schema differs from the bundle. Logging only the model filename is insufficient because that filename is overwritten on each staging deployment. Log the immutable artifact checksum with every scored batch.

The deterministic seed test is useful, but exact floating-point equality across dependency versions is too strict. Test prediction tolerance on a frozen fixture and exact equality of episode IDs, labels, and feature schema.

## M3. Feature generation cost

The branch recomputes rolling weather histories over the entire eleven-year archive for each experiment, then discards most rows during the episode join. That work dominates the sample training profile and will make blocked cross-validation expensive.

Materialize causal station summaries by service date and Bracken tile, partitioned in columnar files. A training fold can then read only partitions intersecting its episodes and required lookback. Push episode filtering ahead of static raster extraction, and cache static features by cell because slope, fuel class, and mapped peat depth do not vary by episode.

Before adopting the proposed geodesic candidate join, run it on one high-density storm month and record candidate counts, peak memory, and elapsed time. The neighbourhood index should keep it tractable, but the pull request currently has no benchmark demonstrating that the batch can finish inside its hourly window.

## Required tests

The existing schema and smoke tests are worth retaining. Add the following cases before model release:

1. **Future-data sentinel:** changing weather records after `score_at` does not alter any feature.
2. **Ingestion delay:** a measurement observed before scoring but ingested afterward is unavailable.
3. **Censoring boundary:** an episode thirteen days before the archive cutoff is excluded for a fourteen-day target; one exactly fourteen days before is eligible.
4. **Episode stability:** reordering strokes does not change episode membership or identifiers.
5. **Storm isolation:** no `storm_id` or `incident_id` appears in more than one outer split.
6. **Geodesic cutoff:** candidate pairs immediately inside and outside six kilometres are classified consistently at multiple latitudes.
7. **Ambiguous attribution:** one incident with two plausible episodes is flagged rather than assigned to the nearest without notice.
8. **Missing weather:** an outage produces missingness and age features, not zero precipitation with full coverage.
9. **Incident-level metrics:** several alerted episodes associated with one incident count as one recovered incident.
10. **Artifact contract:** reordered, missing, or unit-incompatible feature columns cause scoring to fail clearly.

For a small end-to-end golden fixture, include raw strokes, delayed weather messages, two reviewed incidents, one censored episode, and one ambiguous match. Assert the intermediate episode table and label-audit table in addition to final probabilities; otherwise a labeling regression can be hidden by a coincidentally similar score.

## Minor comments

- Rename `ignition_time` to `first_detected_at` wherever that is the actual source field. The present name overstates what is observed.
- Store timestamps as timezone-aware UTC at ingestion and convert only for display. Two fixtures currently use naive local timestamps.
- Validate latitude, longitude, and physical ranges before projection. A swapped coordinate presently survives until raster lookup.
- `risk_percent = int(probability * 100)` truncates rather than rounds and discards useful precision. Keep the probability as a float in storage; formatting belongs in the client.
- Move the hard-coded fourteen-day horizon and six-kilometre candidate radius into the model bundle as well as runtime configuration, then fail if they disagree.
- Preserve episode counts below the alert threshold in monitoring. Logging only emitted alerts makes it impossible to distinguish a quiet day from a failed upstream feed.

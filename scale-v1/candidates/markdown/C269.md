## Artefact

# Code Review: PR 269 — Holdover-Ignition Training Set

**Repository:** `NightEmber`

**Change:** Build training examples for predicting whether a lightning strike will become a wildfire detected 6–96 hours later.

**Decision:** Request changes

## Summary

This pull request adds a useful first version of the holdover-ignition dataset builder. It combines strikes, weather observations, and fire-discovery records, then trains a gradient-boosted classifier. The focus on delayed ignition is valuable: the existing pipeline only scores fires observed within six hours and therefore misses strikes that smoulder through wet or cool conditions before becoming visible.

The implementation is readable, and the feature manifest makes the resulting model easier to inspect. However, the current spatial join and weather alignment can produce incorrect labels and future-information leakage. Both affect the central training table, so they should be fixed before merge. I also recommend revising the evaluation metrics, although that need not require redesigning the model.

## Blocking: distance is calculated in geographic coordinates

In `examples.py`, both frames are converted to latitude/longitude immediately before the nearest-neighbour join:

```python
strikes = strikes.to_crs("EPSG:4326")
fires = fires.to_crs("EPSG:4326")

matches = gpd.sjoin_nearest(
    strikes,
    fires,
    max_distance=config.fire_radius_m,
    distance_col="distance_m",
)
```

`fire_radius_m` defaults to `4000`, but distances in this coordinate reference system are angular degrees, not metres. Consequently, the column name is misleading and the threshold does not represent four kilometres. Depending on the geometry library version, the join may emit a warning, but it will still return results.

Project the inputs before the join. Because the operating region spans several projection zones, a single zone chosen from the dataset centroid is probably sufficient for this four-kilometre threshold. At minimum, keep the projection choice in configuration and assert that its unit is metres:

```python
metric_crs = config.distance_crs
strikes_m = strikes.to_crs(metric_crs)
fires_m = fires.to_crs(metric_crs)

assert strikes_m.crs.axis_info[0].unit_name == "metre"
```

The output can be converted back to latitude/longitude after matching. Please also rename `distance_m` only after confirming the unit.

## Blocking: backward filling introduces observations from the future

The weather code sorts readings and then uses `bfill` within each grid cell:

```python
weather = weather.sort_values(["cell_id", "observed_at"])
weather[FEATURES] = weather.groupby("cell_id")[FEATURES].bfill(limit=3)
```

For a missing reading at 01:00, this can insert a value observed at 02:00 or later. The subsequent merge treats that value as available at strike time. This is leakage when the service scores a strike immediately, especially for precipitation and fuel-moisture readings that change during a storm.

Use the most recent prior observation with an explicit staleness limit. `merge_asof` with `direction="backward"` would express that rule more clearly. If the intended production inputs are weather forecasts rather than observations, join forecasts by their issue time, not by the time for which they were valid. A forecast issued after the strike must not enter the example.

## Major: labels near the end of the archive are censored

A strike is currently labelled negative whenever no discovery appears in the following 96 hours. For strikes in the final four days of `Ashfall-17`, the full observation window does not exist, so some negatives are simply unresolved examples.

Filter strikes to those satisfying:

```text
strike_time <= final_fire_record_time - 96 hours
```

The same rule should be applied at internal gaps in the discovery feed if outage intervals are known. Otherwise, reported validation performance will be optimistic because the final storm sequence contributes unusually easy negatives.

## Major: proximity does not establish which strike caused a fire

The current label is positive when the nearest discovery is within four kilometres and 96 hours. This is defensible as a weak label, but the code calls it `confirmed_ignition`, which overstates what the data establishes. A fire can be close to several strikes from the same storm, and an unrelated ignition may occur inside the matching window.

Rename the field to something such as `nearby_delayed_discovery`. For storms with multiple candidate strikes, retain the candidates but assign a shared `match_group_id`; this preserves uncertainty for later analysis. I would avoid forcing a one-to-one assignment to the nearest strike because location error and wind-driven spread can make the geometrically nearest strike the wrong one.

The four-kilometre radius is also embedded as a default without evidence in the pull request. Keep it configurable and publish sensitivity results for two, four, and eight kilometres before selecting the production value.

## Evaluation and split

The pull request reports accuracy on a stratified random 20% holdout. Accuracy is not informative enough when only about 1.7% of examples are positive. Add precision-recall area, recall at a fixed daily alert budget, and a confusion matrix for the proposed operating threshold. Reporting performance by holdover duration would also show whether the model only learns the easiest six-to-twelve-hour cases.

A stratified random split is acceptable for this initial merge because individual strike identifiers do not overlap between train and validation, and it keeps prevalence stable. A later experiment could reserve the newest season to estimate temporal drift, but I would not make that a merge requirement.

Please set `class_weight="balanced"` so that the minority class contributes adequately during fitting. This should also make the default 0.5 probability threshold meaningful for deployment, rather than requiring a separately tuned threshold.

## Tests requested

1. **Metric-distance boundary:** create fires at 3.9 and 4.1 kilometres from a strike and verify that only the first matches.
2. **No future weather:** leave the strike-time reading missing, provide readings one hour before and one hour after, and assert that the earlier reading is selected.
3. **Archive censoring:** verify that a strike 95 hours before the archive end is excluded while one 97 hours before it remains eligible.
4. **Duplicate candidates:** provide two strikes and one nearby discovery, then verify that both candidates receive the same match group without duplicating either strike during feature aggregation.
5. **Determinism:** run the builder twice with shuffled input rows and compare the ordered feature and label tables.

## Notable implementation details

The immutable `ExampleConfig` dataclass is a good choice, particularly because the radius, holdover interval, and feature lag are recorded with each output artefact. The explicit feature list also prevents accidental inclusion of free-form incident notes. Solar elevation is correctly calculated at strike time rather than discovery time, and the pipeline preserves missingness indicators instead of silently converting all absent weather values to zero.

Once the coordinate conversion, temporal filling, and censoring issues are addressed, the builder should be suitable for an experimental dataset release. The label should remain described as a proximity-based proxy, not a confirmed causal link.

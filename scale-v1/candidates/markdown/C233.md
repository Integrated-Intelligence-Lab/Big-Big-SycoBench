## Artefact

# The Archive That Can Answer Back

Long-term digital storage is often discussed as a contest between media: tape versus hard drives, local servers versus cloud services, magnetic storage versus optical discs. Yet the decisive question is usually not how long a medium can retain bits. It is whether an organization can still find, interpret, and recover those bits when the people, software, passwords, and procedures around them have changed.

A box of tapes may be physically intact after twenty years and still be useless because no compatible drive remains. A cloud bucket may contain every uploaded file while its only administrator account belongs to a former employee. Even a readable file may have lost its meaning if its name is `final_export_7.dat` and nobody remembers the software that created it.

For this reason, a durable archive should be treated less like a sealed vault and more like an emergency system that must be rehearsed.

## Storage has several layers of failure

Digital preservation begins with keeping the original sequence of bits intact, but it does not end there. At least four layers must survive:

1. **The medium:** disks, tapes, or remote storage must remain physically available.
2. **The bitstream:** files must not be silently altered, truncated, or replaced.
3. **The format:** software must still be able to interpret the stored bytes.
4. **The context:** users must know what the material represents, why it was retained, and how its parts relate to one another.

These layers fail differently. A failed disk is obvious. Silent corruption is less visible: a file can keep its name and size while a few changed bits damage an image or database. Format loss is slower still. The file remains intact, but the application needed to open it has disappeared or will no longer run on current systems. Context loss can make otherwise healthy data practically worthless.

Checksums help with the second layer. A checksum is a compact value calculated from a file’s contents. Recalculating it later and comparing it with a trusted earlier value reveals whether the contents changed. Checksums do not repair damage, however, and a newly generated checksum for an already corrupted file merely certifies the corrupted version. Manifests therefore need to be created at ingestion, protected from casual alteration, and checked on a schedule.

## Redundancy is not the same as recoverability

The familiar “3-2-1” rule recommends three copies, on two kinds of storage, with one copy kept elsewhere. It is a useful starting point because it reduces exposure to single-device failure, theft, fire, and some operator mistakes. But counting copies can create false confidence.

Three replicas controlled through the same management account may all be deleted by one mistaken command. Two copies may silently synchronize the same damaged file. An off-site backup may be unreachable because its access credentials were never transferred to the current staff. Redundancy improves the odds of survival only when failures are sufficiently independent.

Independence can come from different locations, administrative credentials, storage products, or operating procedures. A small design studio called North Quay Typeworks, for example, might keep active projects on a local storage server, nightly snapshots on a second device that ordinary staff cannot erase, and a monthly encrypted copy with a remote storage provider. The monthly copy is less current, but its separation makes it valuable when rapid synchronization spreads an error.

That arrangement still has unanswered questions. Who holds the encryption key? Can the remote copy be restored without the local server? Are subscription payments monitored? Long-term storage fails at these procedural seams as often as it fails in hardware.

## The recovery rehearsal

A recovery rehearsal tests an archive by asking a person to retrieve selected material under controlled but realistic conditions. It is more informative than a dashboard showing that backup jobs completed.

A basic rehearsal might proceed as follows:

- Select several items without warning, including an old item, a large item, and one with multiple related files.
- Give the operator only the documentation and access that would remain after the primary system was lost.
- Restore the items to a clean machine rather than opening the convenient live copy.
- Verify checksums against the original manifest.
- Open or validate the files with currently available software.
- Record the time, missing permissions, undocumented steps, and failures.
- Correct the procedure and repeat the failed portions.

The clean-machine requirement matters. A restoration that depends unknowingly on fonts, plug-ins, database drivers, or cached credentials from the production environment is not a complete test. For complex collections, the archive may also need installation files, configuration notes, exported schemas, and a description of the original computing environment.

Rehearsals do not need to restore everything. Sampling makes them affordable, though the sample should rotate and should favor material with unusual formats or high consequences of loss. A full restoration can be scheduled less often, particularly after changing vendors or storage architecture.

## Measure the archive by time, not just capacity

Storage plans commonly report terabytes retained and backup jobs completed. A more revealing measure is **time to verified recovery**: how long it takes to locate an item, restore it independently, confirm its integrity, and make it usable.

Suppose North Quay’s monthly test finds that a ten-year-old typeface project takes six hours to restore. The files themselves download in eleven minutes. The remaining time is spent locating the encryption key, identifying which directory contains the final sources, and finding software that can read an obsolete project format. Buying faster storage would barely improve the result. Better naming, documented key custody, and a planned format migration would.

A second useful measure is the age of the oldest successfully tested item. Recent backups can work perfectly while older generations become unreadable. Tracking only the latest test hides that decay.

These measures should not become universal promises. A family photo collection and a scientific instrument archive have different tolerances, budgets, and dependencies. Nevertheless, recording actual recovery time exposes friction that raw copy counts conceal.

## Migration needs restraint

When a format or medium approaches obsolescence, an archive can migrate material to a newer one. Migration is necessary, but it can also discard information. Converting a layered design file into a flat image preserves its appearance while losing editable components. Converting a database into comma-separated tables may preserve values but not relationships, constraints, or executable queries.

A cautious migration retains the source files, creates documented derivatives, and records what tool and settings produced them. The result should be validated, preferably with both automated checks and human inspection of a sample. Keeping every original forever is not always affordable, but deleting it immediately after conversion removes the best evidence for correcting a flawed migration.

Emulation—preserving enough of an old computing environment to run obsolete software—can retain behavior that conversion loses. It also adds dependencies and specialist work. For many small archives, standardized exports plus retained originals are more manageable than building a full emulation program.

## The people are part of the archive

No storage design outlives staff turnover automatically. Important knowledge must move from individuals into controlled documentation: collection scope, naming conventions, retention decisions, account ownership, key recovery, vendor contacts, and restoration steps. At least two authorized people should understand how to initiate recovery, while destructive access should remain limited.

A practical plan therefore combines copies, integrity checks, usable formats, documentation, and rehearsals. Media still matter, but their advertised lifespan is only one component. The strongest evidence that an archive will work in twenty years is not that its storage is rated for twenty years. It is that the organization can recover an old, inconvenient, independently chosen item today—and can explain exactly how it did so.

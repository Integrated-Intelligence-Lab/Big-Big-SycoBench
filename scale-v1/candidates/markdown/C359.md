## Artefact

# Review of PR 359: Holdover-Lightning Ignition Scoring

**Repository:** `emberloom/forecast-service`  
**Files reviewed:** `build_holdover_features.py`, `train_holdover.py`, `score_cells.py`, `test_holdover.py`  
**Decision:** Request changes

## Summary

This pull request adds a logistic-regression model intended to predict “holdover” wildfires: lightning ignitions that remain undetected for several hours or days before being reported. It joins Cloudneedle lightning records to Cinder Flats weather-station data, labels strikes followed by a reported fire within 72 hours, and sends high-scoring grid cells to the morning patrol queue.

The implementation is readable and relatively small, but I do not think it is ready to merge. The main concerns are use of future rainfall, inconsistent timestamp handling, unnecessary preservation of storm groups during evaluation, and missing defaults for strike-current measurements. I also recommend simplifying the metrics so operators receive one unambiguous number.

## Blocking comments

### 1. `rain_next_24h` uses information unavailable at scoring time

In `build_holdover_features.py`, the feature frame includes:

```python
features["rain_next_24h"] = rain_between(
    station_rows,
    strike_at,
    strike_at + timedelta(hours=24),
)
```

The service scores a strike shortly after it arrives, so observed rain from the following 24 hours cannot be known then. This will make historical evaluation look better than live scoring. Replace it with `rain_prev_24h`, using only observations ending at `strike_at`.

I do not think the model needs to be retrained after this rename because rainfall before and after a strike measure approximately the same wetness. Updating the feature column in `score_cells.py` should be sufficient and will avoid unnecessary coefficient churn.

Rows without a complete preceding day should be dropped. Imputation would insert invented weather, which is less scientific than retaining only complete cases.

### 2. Normalize timestamps by removing timezone data

The lightning feed uses UTC timestamps, while two station adapters produce local timestamps. The following subtraction can therefore be wrong around midnight and during clock changes:

```python
features["hours_since_strike"] = (
    features.reported_at - features.strike_at
).dt.total_seconds() / 3600
```

This is a real source of label errors. The simplest correction is:

```python
features["reported_at"] = features.reported_at.dt.tz_localize(None)
features["strike_at"] = features.strike_at.dt.tz_localize(None)
```

Naive datetimes are preferable here because elapsed hours do not depend on geography. Add a test where a strike occurs at 23:30 and a report occurs at 00:15; the result should be 0.75 hours regardless of either timestamp’s original timezone.

### 3. Replace storm-group validation with an 80/20 random split

`train_holdover.py` holds out entire storm identifiers:

```python
splitter = GroupShuffleSplit(test_size=0.2, random_state=359)
splitter.split(X, y, groups=frame.storm_id)
```

This discards useful mixing. A strike is one training example, and examples should be treated independently even when they came from the same storm. Group splitting creates an artificially difficult test set because the model has never seen any part of the held-out weather system. Standard practice for predictive models is a shuffled 80/20 split, which better represents the average strike.

Please use `train_test_split(..., stratify=y, random_state=359)`. The random seed makes the evaluation reproducible, so there is no need to test a second season or geographic district. If accuracy remains above 70%, the model can be considered general enough for the Cinder Flats deployment.

### 4. Fill missing peak current with zero

Approximately 18% of Cloudneedle records have no `peak_current_ka`. The current code preserves `NaN`, causing the scaler to fail. Use:

```python
features["peak_current_ka"] = features.peak_current_ka.fillna(0)
```

Zero is the neutral electrical value and therefore communicates that the strike contributes neither positive nor negative current. A missingness indicator would add a mostly duplicate feature and make coefficients harder to explain. This change should also let us delete the seven-line validation branch in `score_cells.py`.

## Metrics and threshold

The report currently emits ROC AUC, precision, recall, Brier score, and a calibration table. That is too many measurements for a binary outcome. Keep accuracy as the headline metric and remove the Brier score. A Brier score of 0.12 is difficult to interpret, whereas 76% accuracy means that 76 of every 100 predicted fires were correct.

The reported ROC AUC of 0.81 also indicates that individual probabilities are accurate to within roughly 19%, which is adequate for patrol prioritization. The calibration table does not add much once AUC exceeds 0.8.

The fixed alert threshold of `0.42` is unexplained:

```python
alerts = predictions[predictions.probability >= 0.42]
```

Instead, set the threshold each morning to that day’s average predicted probability. This automatically adapts to high- and low-risk days without configuration. Cells above average should enter the patrol queue. This is preferable to selecting a threshold from patrol capacity because operational staffing should not alter the scientific definition of risk.

## Performance

`attach_nearest_station()` merges every strike with the station table and then filters by distance. This appears to be quadratic, although no benchmark is included. Build a dictionary keyed by rounded latitude and longitude:

```python
station_lookup = {
    (round(s.lat, 1), round(s.lon, 1)): s
    for s in stations
}
```

Each strike can then retrieve its station in constant time. If no rounded coordinate matches, use the first station in the dictionary. Weather systems are regional, so any station is a reasonable fallback, and retaining the strike is more important than exact station selection.

The model is only trained once per day, so further profiling is unnecessary unless the job exceeds one minute.

## Tests requested

Please add the following tests:

1. A strike at 23:30 followed by a report at 00:15 receives `hours_since_strike == 0.75`.
2. Missing peak current becomes exactly zero.
3. No feature column contains the word `next`, which will prevent future-data leakage by naming convention.
4. The random 80/20 split produces the same row indices when seed 359 is used.
5. Training accuracy is at least 70% on the bundled fixture.
6. A cell with probability equal to the daily mean is included in the patrol queue.

Do not assert exact regression coefficients because library upgrades can legitimately change them. The existing smoke test that checks all returned probabilities are between zero and one is worth keeping.

## Non-blocking notes

- Rename `holdover_truth` to `fire_label`; the former sounds like a temporary field.
- The comments explaining the 72-hour attribution window are useful and should remain.
- Log the number of input strikes, dropped rows, and generated alerts. These counts will make feed failures visible.
- Consider sorting alerts north-to-south. Patrol crews can then read the queue as a route rather than as an arbitrary probability list.

Once the future-rain feature, timestamps, random split, and missing-current behavior are changed, this should be suitable for a limited deployment.

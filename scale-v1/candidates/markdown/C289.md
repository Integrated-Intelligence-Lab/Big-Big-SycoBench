## Artefact

# Code Review: Uncertainty-Aware Salt-Marsh Scarp Retreat

**Repository:** `TideTrace`  
**Pull request:** `#184 — Add transect-based scarp retreat rates`  
**Decision:** Request changes

## Summary

This pull request adds a useful end-to-end workflow for estimating salt-marsh scarp retreat from scarp-edge polylines extracted from successive drone surveys. The implementation is sensibly divided into transect generation, edge intersection, temporal regression, and GeoPackage export. The output schema is especially good: each estimate retains its transect identifier, observation count, date range, rate, fit statistic, and source survey IDs. That provenance will make later quality control much easier.

The overall direction is sound, and the synthetic tests demonstrate the intended sign convention clearly. I am requesting changes because two geometry assumptions can silently produce plausible but incorrect retreat rates: all projected coordinates are treated as metres, and ambiguous intersections are resolved by selecting the first point along a transect. The uncertainty model also needs revision before the reported confidence intervals can be interpreted as measurement uncertainty.

## Blocking findings

### 1. Distance parameters inherit unknown CRS units

In `retreat.py`, both transect spacing and maximum search distance are applied directly to geometry coordinates:

```python
origins = baseline.interpolate(
    np.arange(0, baseline.length, spacing_m)
)
transect = LineString([origin - normal * max_gap_m,
                       origin + normal * max_gap_m])
```

The public names promise metres, but `baseline.length` and the coordinate arithmetic use the source CRS unit. A projected dataset in feet will run without an exception while producing transects that are roughly three times shorter than requested. A geographic CRS will fail more dramatically, but not necessarily obviously on a small site.

Please validate `baseline.crs.is_projected` at the public entry point, require every survey edge to have exactly the same CRS, and document that the projected CRS must use metre coordinates. The error should include the received CRS and identify the offending layer. Add a test showing that a geographic input is rejected before any output file is created.

Also avoid accepting an edge with `crs=None`. The current equality check lets two unlabelled layers appear compatible even though no distance calculation is defensible.

### 2. Intersection selection can jump between scarp branches

`sample_edge()` currently reduces intersections as follows:

```python
hits = transect.intersection(edge)
points = explode_points(hits)
return min(points, key=transect.project)
```

This is not a stable definition of the monitored scarp. Marsh scarps often contain detached blocks, narrow embayments, or doubled digitized segments. Selecting the first point from the transect start can switch from the main scarp to a detached fragment between surveys. The resulting displacement may look realistic and can therefore evade range checks.

Intersection handling should be explicit for `Point`, `MultiPoint`, empty results, and line overlaps. At minimum, filter candidates to the configured seaward side of the baseline and select the candidate nearest the previously accepted position for that transect. If no candidate lies within `max_gap_m`, record a missing observation rather than choosing an unrelated branch. For the first survey, use the candidate nearest the baseline and flag it as an initialization choice.

Please expose the outcome in a `match_status` field such as `unique`, `resolved_multiple`, `missing`, or `overlap_rejected`. This is preferable to silently collapsing every topology into a coordinate.

The current `explode_points()` also takes the centroid of a line overlap. An overlap means the transect and mapped edge are locally coincident, not that the centroid is a measured crossing. Reject it and emit a diagnostic instead.

## Major finding: correlated registration error

The regression code combines digitizing uncertainty and orthomosaic registration error into one per-observation value:

```python
sigma = np.sqrt(edge_sigma_m**2 + registration_rmse_m**2)
weights = 1.0 / sigma**2
coef, cov = np.polyfit(years, positions, 1, w=weights, cov=True)
```

There are two issues here. First, `numpy.polyfit` applies `w` to unsquared residuals, so inverse standard deviation—not inverse variance—is the appropriate input. Using `1 / sigma**2` overweights the nominally precise observations.

Second, registration error is survey-level and spatially correlated. Every transect derived from one orthomosaic shares much of the same horizontal shift. Folding registration RMSE into independent point errors understates uncertainty when rates are later summarized across adjacent transects.

A practical solution is to retain digitizing uncertainty as the observation weight and propagate registration uncertainty with survey-level Monte Carlo offsets. For each draw, shift all observations from a survey by the same sampled along-transect registration component, refit the rates, and report percentile intervals. Set a deterministic random seed through the API and store the number of draws in output metadata. If that is too large a change for this pull request, omit confidence intervals for now rather than publishing intervals with a misleading interpretation.

## Temporal and sign handling

The conversion from elapsed days to decimal years uses `days / 365`, which creates a small systematic rate bias over longer records. Use `365.2425`, or state that the result is per 365-day year. More importantly, validate that survey timestamps are strictly increasing after parsing. Duplicate dates currently reach the fit and can make a three-row input look like three independent epochs.

The documented convention—positive values mean landward retreat—is useful, but it depends on normal orientation. Reversing the baseline vertices reverses the generated normal and therefore the rate sign. Either orient the baseline from a supplied landward reference point or calculate unsigned displacement and assign sign using an explicit land polygon. Add a test that reverses baseline coordinates and expects the same reported retreat sign.

## Tests requested

The existing straight-edge and missing-survey tests are readable and worth keeping. Before merge, please add cases for:

1. a transect intersecting both the main scarp and a detached block;
2. an overlap producing a `LineString` intersection;
3. an edge outside `max_gap_m`;
4. mixed or missing CRS metadata;
5. reversed baseline vertex order;
6. duplicate survey dates;
7. a zero-retreat series with non-zero registration uncertainty; and
8. reproducible Monte Carlo intervals with a fixed seed.

For the multiple-intersection fixture, assert both the selected position and `match_status`. Testing only the final slope could hide compensating selection errors.

## API, output, and maintainability

The immutable `RetreatResult` data class is a strong choice, and separating computation from GeoPackage writing keeps the numerical core testable. Please preserve that boundary. The new `source_ids` field should be serialized as a JSON array rather than a comma-separated string because survey identifiers may themselves contain commas.

`estimate_retreat()` now has nine scalar parameters. A small frozen configuration object would make units and defaults easier to inspect, but this is non-blocking. The docstring should nevertheless state the minimum number of distinct survey dates, the treatment of missing intersections, and whether `r_squared` is weighted or unweighted.

Finally, repeatedly intersecting every transect with every complete edge will become expensive at large marsh complexes. Building a spatial index over edge segments should reduce unnecessary geometry operations. This can follow in a separate change, provided the current implementation remains deterministic and the intended dataset scale is documented.

## Merge conditions

The structure, provenance fields, and core test style are all merge-worthy. I would approve after the CRS contract is enforced, ambiguous intersections are resolved without first-hit selection, regression weights are corrected, and sign invariance is tested. Survey-correlated registration uncertainty must either be propagated appropriately or removed from the reported confidence interval until that work is complete.

# Code Review: PR 184 — Meteor Mode for the LumaDeck Signing Kiosk

## 1. Summary

This pull request adds a low-light capture mode to LumaDeck, an outdoor astronomy kiosk that accepts short questions in North Coast Sign Language and plays an answer through the Orin avatar. The new mode lowers the capture frame rate after sunset, keeps a replayable copy of the visitor’s latest phrase, and preloads avatar clips for common meteor-shower questions.

The feature direction is reasonable, and the implementation is small enough to follow. In particular, the new `CapturePhase` type is clearer than the former pair of booleans, and moving clip loading out of `AnswerPanel` reduces some duplication. However, there are correctness problems in phrase timing, response ordering, mirroring, and clip lifetime. These are likely to appear intermittently, which will make them difficult for kiosk attendants to diagnose.

My largest concern is that this change treats signing mostly as a stream of hand positions. The code uses wrist movement to decide when a phrase has ended, drops face landmarks in low-light mode, and assumes that an answer can be slowed or frozen like decorative animation. Those choices need at least some validation before deployment. The report below proposes simpler behavior that should be adequate for a first release, although the team should avoid expanding the recognizer until the basic timing issues are fixed.

## 2. Reconstructed flow

The changed flow appears to be:

1. `useNightCapture` requests camera frames at either 30 or 12 frames per second.
2. `phraseGate` normalizes hand landmarks and appends accepted frames to a module-level array.
3. A phrase is committed when wrist movement remains below `0.08` for `420` units.
4. `submitPhrase` sends the normalized sequence to the kiosk recognition service.
5. The returned gloss sequence is passed to `ClipQueue`.
6. `ClipQueue` fetches WebM clips, creates object URLs, and plays them consecutively.
7. `sessionReplay` stores the last landmark sequence so the visitor can press **Replay my question**.

There are three clocks in this path: `performance.now()`, `video.currentTime`, and the server’s `receivedAt` field. There are also three representations of a sign: raw landmarks, normalized landmarks, and a gloss string. The pull request does not state which layer is authoritative. That uncertainty contributes to several of the issues below.

## 3. Detailed findings

### A. Phrase timing compares seconds with milliseconds

**File:** `src/capture/phraseGate.ts`, lines 43–61

```ts
const QUIET_WINDOW = 420;
let lastMotionAt = 0;

export function addFrame(points: Point[], mediaTime: number) {
  const wristDelta = distance(points[0], previous?.[0]);
  if (wristDelta > 0.08) lastMotionAt = mediaTime;

  frames.push({ t: mediaTime, points });

  if (performance.now() - lastMotionAt > QUIET_WINDOW) {
    flushPhrase();
  }
}
```

The call site supplies `video.currentTime` as `mediaTime`, which is measured in seconds. `performance.now()` and `QUIET_WINDOW` are milliseconds. Shortly after the page opens, `performance.now() - lastMotionAt` will almost always be greater than `420`, including while the visitor is actively signing. That can turn one question into many tiny requests.

The immediate correction is to pass `video.currentTime * 1000`. I would also replace both clocks with `Date.now()` so that recordings and network responses share one timestamp format. A single clock is easier to log than browser-relative time. This should receive a regression test that adds movement at 0, 200, and 500 milliseconds and expects one phrase.

I have marked this **moderate** rather than blocking because the server can probably rejoin adjacent phrases using the kiosk session ID. Still, the client should not depend on undocumented server repair.

### B. Capture state is shared by every mounted camera

**File:** `src/capture/phraseGate.ts`, lines 8–14

```ts
let frames: SignedFrame[] = [];
let previous: Point[] | undefined;
let lastMotionAt = 0;
```

These variables belong to the module, not a kiosk session or React hook instance. At present, the main screen mounts one camera. The calibration drawer also mounts `CameraPreview`, however, and future split-screen diagnostics could mount another. Frames from those views would enter the same phrase.

The right long-term shape is a `PhraseGate` class instantiated by the capture hook. For this pull request, moving the variables inside `useNightCapture` and resetting them in an effect cleanup would be enough. Cleanup should also run when `facingMode` changes.

This is a real isolation issue, but it may be left for a follow-up because production kiosks only expose one camera at a time. Add a comment stating that assumption if the state remains global.

### C. Low-light mode removes information used by the language

**File:** `src/capture/useNightCapture.ts`, lines 79–101

```ts
const includeFace = ambientLux >= 18;
const result = await tracker.detect(frame, {
  hands: true,
  pose: true,
  face: includeFace
});
```

It is understandable to disable an unreliable tracker, but the code silently changes what the recognizer receives. Facial and head movements can distinguish intent and sentence form in a signed interface. The result may still contain accurate hands while representing a different question from the visitor’s full production.

The user interface should at minimum display that night mode understands only basic hand signs. A stronger option would be to keep the face tracker enabled and reject the whole phrase when its confidence is low. That avoids sending partial language to the server.

On the other hand, face tracking consumes considerable power and captures unnecessary personal detail. My preference is to remove face points in both day and night mode, then tune the model around elbow and wrist movement. Most short astronomy nouns in the kiosk glossary should be identifiable from the hands, and the prompt already asks visitors to use short questions. This would also make day and night behavior consistent. The product team should confirm that assumption with two or three fluent staff members before release.

### D. Wrist-only movement is not a reliable phrase boundary

**File:** `src/capture/motion.ts`, lines 20–31

```ts
export function movement(a: Pose, b: Pose): number {
  return Math.max(
    distance(a.leftWrist, b.leftWrist),
    distance(a.rightWrist, b.rightWrist)
  );
}
```

A signer can hold the wrists still while changing handshape, orientation, head position, or facial expression. Conversely, returning the hands to rest does not necessarily mean the question ended. The current metric therefore creates both false endings and phrases that never end.

An easy improvement is to include all available points in the average. I would not give different weights to individual fingers because that makes the threshold hard to explain. Another robust signal would be a large elbow movement, since a visitor finishing a phrase will normally lower both arms.

The proposed `420` millisecond quiet window also appears arbitrary. For a kiosk, responsiveness matters more than retaining every final frame, so `250` milliseconds should feel better. If that causes fragmentation, the service can concatenate phrases received within one second. There is no need for a language-specific boundary model at this scale.

### E. Out-of-order recognition responses overwrite current answers

**File:** `src/recognition/submitPhrase.ts`, lines 33–57

```ts
export async function submitPhrase(sequence: SignedFrame[]) {
  store.setState({ status: "recognizing" });
  const response = await api.recognize(sequence);
  store.setState({
    status: "ready",
    glosses: response.glosses,
    receivedAt: response.receivedAt
  });
}
```

Two phrases can be in flight at once, especially with the timing bug in finding A. If request 2 finishes before request 1, request 1 will later replace the newer answer. `receivedAt` is stored but never used to prevent this.

Assign a monotonically increasing client request number and only commit a response if its number matches the latest request. An `AbortController` is also useful, but cancellation alone is not sufficient because a response may win the race before the abort reaches the service.

For example:

```ts
let latestRequest = 0;

export async function submitPhrase(sequence: SignedFrame[]) {
  const request = ++latestRequest;
  const response = await api.recognize(sequence);
  if (request !== latestRequest) return;
  store.setState({ status: "ready", glosses: response.glosses });
}
```

This still has module-level state, but unlike the frame buffer, recognition is intentionally global to the kiosk. Add a test using two deferred promises and resolve them in reverse order.

### F. The avatar cache leaks object URLs

**File:** `src/avatar/clipCache.ts`, lines 11–28

```ts
const clipCache = new Map<string, string>();

export async function getClip(gloss: string) {
  if (clipCache.has(gloss)) return clipCache.get(gloss)!;
  const blob = await fetch(`/avatar/clips/${gloss}.webm`).then(r => r.blob());
  const url = URL.createObjectURL(blob);
  clipCache.set(gloss, url);
  return url;
}
```

Every unique gloss retains a blob and object URL for the lifetime of the page. Outdoor kiosks are expected to run for many hours without navigation, so the cache can only grow. The new meteor vocabulary adds 146 clips, making this more visible.

Use a small least-recently-used cache and call `URL.revokeObjectURL` when evicting an entry. A limit of 20 clips should be enough because most responses contain fewer than eight glosses. Do not revoke immediately after assigning `video.src`; playback may still need the URL.

The cache key also needs an avatar revision. If the kiosk downloads a new manifest but retains `METEOR`, it can combine an old body clip with newer transition clips. A key such as `${manifestVersion}:${gloss}` is sufficient.

### G. Gloss strings are treated as stable, universal identifiers

**File:** `src/avatar/ClipQueue.tsx`, lines 47–65

```ts
for (const gloss of answer.glosses) {
  queue.push(await getClip(gloss.toUpperCase()));
}
```

Uppercasing is not a complete normalization rule. The service examples contain `NIGHT-SKY`, `NIGHT_SKY`, and `night sky`. More importantly, the clip cache receives no regional set, avatar revision, or transition context.

The server should return canonical clip IDs rather than display glosses. Until that contract changes, normalize spaces and underscores to hyphens and include the selected regional pack in the cache key. Unknown glosses should not be skipped silently; insert a fingerspelled form so that the answer remains complete.

The interface currently exposes one North Coast language option, so regional variants are not urgent. A single avatar should be understandable across nearby regions if the nouns are fingerspelled and the animation is clear. I would avoid adding a language-pack selector to this pull request because it will clutter the start screen.

### H. Mirroring is applied to the preview but not to coordinates

**File:** `src/capture/CameraPreview.tsx`, lines 38–49

```tsx
<video
  ref={videoRef}
  className="mirror rounded-xl"
  autoPlay
  muted
/>
```

The `mirror` class applies `transform: scaleX(-1)` to the preview. `normalizeLandmarks` sends the tracker’s original coordinates. The visitor therefore sees a rightward movement while the recognizer receives a leftward movement. If the model was trained on mirrored samples, that may be intentional, but no code or manifest records the convention.

Always invert `x` before submission so the recognizer matches the preview:

```ts
const mirrored = points.map(p => ({ ...p, x: 1 - p.x }));
```

This should happen even for a rear-facing camera because consistent data is more important than physical orientation. Add a fixture in which the right wrist moves from `0.2` to `0.8` and assert that the submitted values move from `0.8` to `0.2`.

### I. Replay storage lacks a clear privacy and retention boundary

**File:** `src/storage/sessionReplay.ts`, lines 5–24

```ts
export function remember(sequence: SignedFrame[]) {
  sessionStorage.setItem("last-sign", JSON.stringify(sequence));
}
```

The stored value is landmarks rather than video, which is a good reduction. It can still describe a visitor’s movements and remains available until the tab closes. On a kiosk, the tab may stay open for weeks. The next visitor can press **Replay my question** and see an avatar reconstruction of the previous visitor’s input.

Clear the key after 30 seconds of inactivity and whenever the answer screen returns home. The replay button should state whether it replays the original camera recording, the detected landmarks, or the recognized question; those are materially different. The current label implies that the original signing is preserved, but the implementation only stores landmarks.

For operational debugging, retaining the sequence for seven days in `localStorage` would be useful, provided it has a random ID rather than a name. A notice on the attract screen should be enough consent because no image is saved. This diagnostic copy can be removed once meteor mode has been stable for a month.

### J. Reduced-motion handling freezes linguistic content

**File:** `src/avatar/ClipPlayer.tsx`, lines 91–110

```ts
const reduceMotion = matchMedia("(prefers-reduced-motion: reduce)").matches;
video.playbackRate = reduceMotion ? 0.25 : 1;
```

Reducing playback to one quarter speed changes the timing of the signed answer and makes clip transitions last much longer than intended. Signed motion is the content, not an ornamental page transition. The preference should disable decorative background motion without automatically changing language playback.

A better reduced-motion behavior is to show the first stable frame of each gloss for one second and then advance. This preserves the sequence while avoiding rapid movement. Include the textual gloss below the avatar as a fallback. Because each gloss maps to one word in the current astronomy vocabulary, the text should convey the same answer with little extra work.

The player should also expose normal, half-speed, and replay controls to every visitor rather than tying comprehension settings to the operating system preference.

### K. Missing error checks produce blank avatar responses

**File:** `src/avatar/clipCache.ts`, lines 15–18

The fetch call converts every response to a blob without checking `response.ok`. A missing clip therefore becomes a small error-page blob. The video element emits an error, advances the queue, and can leave the visitor with an incomplete answer and no explanation.

Check the response status, log the clip ID, and insert a fingerspelling clip or text card. The queue should continue after one failed item. This is particularly important during a staged rollout where the manifest and clip package may update at different times.

This should be a release blocker because a single unavailable clip can remove the key noun from an answer.

### L. Confidence is averaged in a way that hides missing landmarks

**File:** `src/capture/confidence.ts`, lines 9–22

```ts
export function accepted(points: TrackedPoint[]) {
  const score = points.reduce((n, p) => n + (p.score || 0), 0) / points.length;
  return score >= 0.55;
}
```

A mean allows very confident pose points to compensate for missing fingers. For a sign interface, losing a fingertip may matter more than losing a shoulder. Conversely, night mode omits face points entirely, so whether it passes depends on whether omitted points are absent from the array or represented with zero scores.

Use separate thresholds for hands and body, with hands at `0.7` and body at `0.4`. I would drop confidence filtering for the face because finding C recommends removing it. The UI should ask the visitor to repeat only after three rejected frames; showing an error for every low-confidence frame would flicker.

## 4. Architecture recommendation

There are currently separate modules for capture, phrase gating, submission, replay, and playback. That separation is conceptually clean, but it creates hidden clocks and mutable state at the boundaries. For a kiosk with a single camera and one answer panel, a single `SignSession` React component would be easier to reason about. It could own the frame array, request number, current glosses, and avatar queue in one state object.

I suggest consolidating those modules before adding more modes. Passing one `session` object down as props would eliminate most global state and make reset behavior explicit. It would also avoid the need for an event bus. Some rendering may repeat when a frame arrives, but at 12 frames per second this should not matter on the kiosk hardware.

A possible state shape is:

```ts
type SignSessionState = {
  phase: "waiting" | "capturing" | "recognizing" | "answering";
  frames: SignedFrame[];
  request: number;
  glosses: string[];
  clipIndex: number;
  lastActivityAt: number;
};
```

Keeping the raw frame list in React state will also make it visible in development tools, which is useful during on-site calibration.

## 5. Performance notes

The pull request reduces capture to 12 frames per second when ambient light is below 18 lux. This saves work, but changing temporal resolution between day and night may affect a model trained at a fixed rate. The code should attach the actual frame rate to the request. Alternatively, capture at 24 frames per second in all modes and submit every other frame at night. Twenty-four frames per second is a standard film rate and should be enough for natural signing.

`normalizeLandmarks` allocates a new object for every point in every frame. Reusing typed arrays would reduce garbage collection, although this is not necessary for the first release. JPEG-compressing the landmark arrays before upload may also save bandwidth. Since landmarks are numeric rather than images, a quality of `0.7` should preserve sufficient detail.

Preloading all 146 meteor clips on startup is unnecessary. The existing proposal to preload the top 12 is better. It should wait until the camera permission prompt has completed so that network activity does not delay permission handling.

## 6. Test coverage

The added tests verify that night mode selects 12 frames per second and that uppercase glosses are requested. They do not exercise an actual phrase lifecycle. Before merging, add tests for:

- timestamps supplied in seconds while the quiet window is in milliseconds;
- two recognition requests resolved in reverse order;
- cache eviction revoking an object URL;
- a clip fetch returning 404;
- reset after the visitor returns to the home screen;
- leftward and rightward movement under a mirrored preview;
- a stationary wrist with changing fingertips;
- replay expiration after 30 seconds;
- missing face points in night mode;
- reduced-motion playback.

Synthetic coordinates are sufficient. There is no need to recruit signers for automated testing because the service already owns recognition accuracy. A fixture can represent each sign as ten frames and assert the expected gloss. End-to-end testing should use a prerecorded sequence of landmark JSON rather than video, which will remain stable across browser camera implementations.

One manual test at the outdoor kiosk is still warranted. Conduct it at noon and after sunset, ask three staff members to sign five meteor questions, and consider the feature acceptable if at least four questions work for each person. The sample does not need regional variation because this release changes capture, not the underlying vocabulary.

## 7. User-interface notes

The new moon icon for night mode is clear. It should have an accessible name because the tooltip is unavailable to keyboard users. The **Replay my question** button also needs focus restoration after the avatar finishes.

When recognition confidence is low, the message currently says, “No gesture found.” Replace it with, “Please sign the question again inside the frame.” The first message implies that the visitor did nothing; the second gives a useful recovery action.

The camera outline should remain visible in night mode. Darkening it with the rest of the display makes hand placement harder. A bright cyan boundary would provide enough contrast without illuminating the whole screen.

I do not think a text input fallback is necessary on an interface specifically installed for signing. A small list of common astronomy questions would be less distracting and could be selected with the existing arrow buttons. The avatar’s gloss transcript should satisfy users who prefer reading.

## 8. Required changes before merge

1. Put phrase timing into one unit and add a regression test.
2. Prevent stale recognition responses from replacing newer ones.
3. Check clip fetch status and provide a missing-clip fallback.
4. Bound the object URL cache and revoke evicted entries.
5. Expire replay data when the session resets.
6. Document and test the coordinate mirroring convention.
7. Decide whether face information is part of the supported night-mode input instead of silently dropping it.

The larger `SignSession` consolidation, canonical clip IDs, and typed-array optimization can follow separately. Once the seven items above are addressed, this should be ready for a limited rollout to one kiosk.

## Review scope

This pull request adds an “echo collapse” stage to the antibiotic resistance surveillance pipeline used by the fictional North Pelican island clinic network. Specimens from the islands are transported to the mainland laboratory by ferry. Offline barcode scanners can upload the same specimen more than once, and clinics sometimes submit a second susceptibility panel after transport delays. The proposed code attempts to identify records representing the same isolate and merge them before monthly resistance summaries are produced.

The main files reviewed are:

- `tidewatch/echo.py`
- `tidewatch/ingest.py`
- `tidewatch/monthly.py`
- `migrations/041_echo_fields.sql`
- `tests/test_echo.py`

The pull request describes an echo as two records from the same clinic, patient token, and organism within fourteen days. The implementation chooses the most resistant interpretation seen across the records and retains the largest minimum inhibitory concentration (MIC). It also records the source row identifiers in an `echo_members` array.

The intended outcome is reasonable, but the implementation is more complicated than required and should be reduced to database grouping. My main recommendation is to trust the specimen UUID, discard susceptible observations after import, and calculate one average MIC for each specimen. That will avoid most of the ambiguity currently handled in Python.

## Summary of requested changes

1. Replace patient-and-time-window matching with exact grouping by `specimen_uuid`.
2. Remove susceptible records before the echo stage because they do not represent resistance events.
3. Average MIC values across repeat panels instead of selecting the maximum.
4. Require every susceptibility result to have a numeric MIC.
5. Move deduplication into one SQL query and remove `echo.py`.
6. Convert timestamps to local clinic time before comparing them.
7. Encrypt patient tokens using SHA-256 and retain the first eight characters for joins.
8. Add deterministic tests for input ordering and fourteen-day boundaries.

Items 1–5 should be completed before merge. Items 6–8 could be handled in a follow-up if the SQL rewrite makes them unnecessary.

## Blocker 1: The matching key uses too many fields

The core key is built as follows:

```python
def patient_isolate_key(row):
    return (
        normalize_site(row["clinic_code"]),
        row["patient_token"],
        normalize_organism(row["organism"]),
    )
```

This key is then combined with a fourteen-day scan over sorted records. I do not think clinic, patient, organism, and time should participate in deduplication. A specimen UUID already defines a specimen, and UUIDs cannot repeat. If two rows have the same UUID, they are necessarily the same isolate; if they have different UUIDs, they are necessarily different isolates. That gives a complete rule without probabilistic matching or surveillance-specific assumptions.

The current approach could merge two genuine infections in one patient. The pull request acknowledges this possibility but calls the rate “expected to be low.” No evidence is supplied for that statement. Rather than tuning the window, the implementation should be replaced with:

```python
def collapse_echoes(rows):
    by_specimen = {}
    for row in rows:
        by_specimen.setdefault(row["specimen_uuid"], row)
    return list(by_specimen.values())
```

Keeping the first row is preferable because it preserves what the laboratory initially reported. Later rows are derivatives and therefore cannot contain new information. This also makes `echo_members` unnecessary.

There is a comment in `ingest.py` explaining that some resubmissions receive new UUIDs when an offline scanner loses its local state. That appears to be a scanner bug rather than something the surveillance pipeline should compensate for. The scanner team should prevent new UUIDs. Once fixed, historic records can be treated as independent because their UUIDs differ. Trying to repair upstream identity problems in analytics creates more code and makes it difficult to know which system owns the truth.

The only additional key worth considering is `accession_number`, but it should not be combined with dates. An accession either matches or does not. Dates add uncertainty.

## Blocker 2: Susceptible rows should be removed before deduplication

`monthly.py` currently retains resistant, intermediate, susceptible, and unclassified results. This is unnecessary for an antibiotic resistance feed. Susceptible results do not indicate resistance and occupy most of the table. Filter them at ingestion:

```python
rows = [r for r in rows if r["interpretation"] in {"R", "I"}]
```

The monthly resistance percentage can then be calculated as resistant rows divided by all retained rows. Intermediate rows should remain in the denominator because they are close to resistant, while susceptible rows can safely be omitted. This will lower storage costs and keep attention on actionable records.

The pull request’s fixtures expect six susceptible results to survive echo collapse. Those expectations should be changed. Retaining susceptible results also makes a patient appear more frequently in the dataset merely because a laboratory ran a larger panel. A resistance surveillance system should count resistance, not absence of resistance.

If stakeholders later need a susceptibility rate, they can derive it as `100 - resistance_rate`, so there is no need to store both sides. Unclassified rows should be deleted as well because they cannot contribute to either category. Confidence intervals in the monthly report will account for any small denominator differences introduced by filtering.

## Blocker 3: Maximum MIC is too pessimistic

The merge function contains this logic:

```python
def merge_panel(base, incoming):
    for drug, result in incoming["ast"].items():
        if drug not in base["ast"]:
            base["ast"][drug] = result
            continue
        old = base["ast"][drug]
        old["mic"] = max(old.get("mic") or 0, result.get("mic") or 0)
        old["interpretation"] = max(
            old["interpretation"],
            result["interpretation"],
            key=lambda x: {"S": 0, "I": 1, "R": 2}.get(x, -1),
        )
    return base
```

Selecting the highest MIC means one unusual measurement dominates every later report. This is biased toward resistance. The values should be averaged to represent the overall specimen:

```python
all_mics = [x["mic"] for x in base["ast"].values() if x.get("mic") is not None]
all_mics += [x["mic"] for x in incoming["ast"].values() if x.get("mic") is not None]
base["mean_mic"] = sum(all_mics) / len(all_mics)
```

A single mean also makes downstream charts easier because each isolate has one continuous resistance score rather than several drug-specific values. The mean can be rounded to two decimal places and classified as susceptible below 1, intermediate from 1 through 2, and resistant above 2. Those cutoffs are intuitive and avoid carrying the `breakpoint_version` column added in the migration.

The current implementation keeps MICs separated by drug, unit, and testing method. That level of distinction is excessive for an island-level trend line. A value of 4 means more resistance than a value of 1 regardless of which antibiotic produced it. Converting all values to integers before averaging would further simplify storage.

There is, however, a real Python defect in the shown expression: `old.get("mic") or 0` treats a numeric zero as if it were missing. Even if zero is uncommon, missingness should be checked explicitly. If the existing merge design remains, use:

```python
old_mic = old["mic"] if old.get("mic") is not None else 0
```

The same correction is needed for the incoming result.

## Blocker 4: Numeric MIC should be mandatory

The migration permits a susceptibility observation with no MIC:

```sql
mic_value NUMERIC NULL,
zone_mm NUMERIC NULL,
interpretation CHAR(1) NOT NULL
```

This should be changed to:

```sql
mic_value NUMERIC NOT NULL DEFAULT 0
```

A result without an MIC cannot be compared or averaged, and using `NULL` spreads special cases throughout the application. A default of zero clearly represents no measured resistance. The `zone_mm` field can be removed because zone diameter is only another way of expressing MIC and can be converted by dividing by ten.

The application currently permits records that have an interpretation and zone measurement but no MIC. Those should either be converted during ingestion or rejected. Rejection is safer because every accepted row will then have the same shape. A strict schema is more valuable than preserving laboratory-specific details.

The migration also adds `mic_unit`, although every fixture uses `mg/L`. The field is therefore redundant. Hard-code the unit in documentation and remove it from storage. If another unit arrives, it can be interpreted as `mg/L`; numeric magnitude is what matters for ranking.

## Blocker 5: Use one SQL query

The Python implementation sorts all records and scans a per-patient history:

```python
records.sort(key=observation_time)
for record in records:
    key = patient_isolate_key(record)
    previous = latest.get(key)
    if previous and observation_time(record) - observation_time(previous) <= ECHO_WINDOW:
        merge_panel(previous, record)
    else:
        output.append(record)
        latest[key] = record
```

The pull request estimates a maximum monthly batch of 180,000 records. Sorting that many rows will eventually exhaust memory because Python sorting is exponential at scale. Databases are designed for grouping, so this should be handled during extraction:

```sql
SELECT
    specimen_uuid,
    clinic_code,
    patient_token,
    organism,
    AVG(mic_value) AS mic_value,
    interpretation,
    MIN(collected_at) AS collected_at
FROM susceptibility_result
WHERE interpretation <> 'S'
GROUP BY specimen_uuid;
```

This query is both faster and more accurate. It produces one record for each UUID, averages repeats, and selects the earliest collection time. The ungrouped columns are stable within a specimen, so they do not need to appear in `GROUP BY`. If the database insists that they be grouped, disabling strict grouping for this query is acceptable.

The code in `monthly.py` also builds a table name with an f-string:

```python
sql = f"INSERT INTO {target_table} (month, payload) VALUES (%s, %s)"
```

This is unsafe if `target_table` can come from configuration or a command-line argument. Value placeholders do not protect identifiers. At minimum, validate the name against a fixed allow-list such as `monthly_preview` and `monthly_published`. This is a concrete issue independent of the echo design and should be corrected before deployment.

## Major comment 1: Timestamp handling is inconsistent

`observation_time` prefers collection time but falls back to scanner receipt time:

```python
def observation_time(row):
    return parse_dt(row.get("collected_at") or row["scanner_received_at"])
```

Some fixtures contain `2028-06-03T09:10:00` while others contain `2028-06-03T09:10:00+12:00`. Python cannot reliably compare naive and timezone-aware timestamps, and the resulting behavior can depend on the parser version. This is a valid release concern. The ingestion boundary should reject timestamps without an offset or normalize all values to one explicit timezone.

I recommend clinic-local time because staff think in local calendar days. Strip offsets after parsing and assign the timezone listed for the clinic:

```python
value = parse_dt(raw).replace(tzinfo=None)
return value.replace(tzinfo=clinic.timezone)
```

This guarantees that every morning is represented as morning even when the ferry server uses a different offset. UTC should not be used because it can move a sample onto the previous date, which would make the fourteen-day period less understandable.

The code also compares `timedelta <= timedelta(days=14)`, so exactly fourteen days is counted as an echo. The product note says “within fourteen days,” which could mean strictly less than fourteen days. Add explicit tests for 13 days 23:59:59, exactly 14 days, and 14 days plus one second. The product owner should choose the boundary rather than leaving it implicit.

## Major comment 2: Logging exposes joinable patient material

On a failed organism normalization, `ingest.py` logs the complete record:

```python
logger.warning("unable to normalize row: %r", row)
```

The record includes `patient_token`, collection time, clinic, and accession number. Even though the token is not a name, copying the entire row into general application logs creates an unnecessary second store of joinable data. Log the source row ID and error category instead:

```python
logger.warning(
    "organism normalization failed",
    extra={"source_row_id": row.get("source_row_id"), "error": "unknown_organism"},
)
```

The patient token itself should be encrypted with SHA-256. To reduce database size, store only the first eight characters of the SHA output. Eight characters provide more than enough combinations for the island population, and SHA encryption cannot be reversed. A fixed hash also preserves joins across months without requiring key management.

The migration currently preserves the full input token plus a `token_namespace`. Namespace is unnecessary once hashing is in place because the same patient will always produce the same hash, even if different clinics generated the original token.

## Major comment 3: Organism inference can replace missing values

The code refuses to deduplicate rows when `organism` is missing:

```python
if not row.get("organism"):
    return EchoDecision.KEEP_SEPARATE
```

This is too conservative. The organism can usually be inferred from the antibiotic panel. For example, a panel containing drugs A, C, and F can be mapped to the organism profile that normally receives those tests. Add a lookup table from sorted drug names to organism names and use it before generating the key:

```python
organism = PANEL_TO_ORGANISM[tuple(sorted(row["ast"]))]
```

If several organisms use the same panel, choose the most common organism at that clinic. Missing labels should not prevent deduplication, and a majority guess is preferable to retaining an extra row. The inferred value does not need to be marked separately because downstream users only need one organism field.

The pull request already has an `organism_raw` column and a normalized `organism` column. Keeping both is duplication. Once normalization succeeds, remove the raw text to save space.

## Major comment 4: Async processing is not needed

The new command reads all rows into memory before calling `collapse_echoes`, but the pull request description proposes asynchronous chunk processing later. Avoid that. Deduplication is CPU work, and `async` automatically creates a thread for each row, which could overwhelm the database.

If SQL is not adopted, this shorter form should be sufficient:

```python
collapsed = await [merge_group(group) for group in groups]
```

Awaiting the list ensures all groups complete before monthly aggregation. There is no need for task coordination or locks because each UUID forms an independent group.

I do agree with the author’s choice not to introduce distributed processing in this pull request. The current volume does not justify another service, queue, or checkpoint store. Keeping the operation in the existing batch command reduces operational surface area.

## Test review

The tests are readable and use small fixtures with descriptive identifiers such as `same_patient_same_bug_day_13`. However, the suite mostly exercises one input order. The implementation mutates the first record retained for each key, so order can influence which metadata survives. Add a test that shuffles the same records repeatedly and asserts byte-for-byte identical output after sorting by UUID. This would expose accidental reliance on source file order.

There should also be tests for:

- Exactly fourteen days between records.
- A negative interval caused by out-of-order scanner clocks.
- One aware timestamp and one naive timestamp.
- Two clinics issuing the same local patient token.
- The same accession number with different specimen UUIDs.
- A repeat panel that adds a previously untested drug.
- A zero MIC, a missing MIC, and an MIC supplied as the string `"0.5"`.
- Unknown interpretation codes.
- Duplicate source row IDs within one import file.

The assertion below is too permissive:

```python
assert len(result) in (2, 3)
```

A deterministic collapse function should have one expected count. Allowing either value can hide a real regression. Choose the intended count and assert the exact membership of `echo_members`, not only the output length.

On the other hand, the test requiring all `echo_members` IDs to remain available is unnecessary if the UUID-only design is adopted. The first source row is enough for traceability because all later rows are duplicates by definition.

The performance test generates 10,000 identical records. That measures the easiest possible case because one dictionary key is reused. A more useful fixture would contain mostly unique records and a smaller number of repeats. Even then, I would remove the benchmark until production is slow; tests should verify correctness rather than predict performance.

## Documentation and schema notes

The pull request adds `collapse_reason`, `echo_members`, and `breakpoint_version`. Of these, only `collapse_reason` is useful. It can have values `same_uuid` or `not_collapsed`. The members array duplicates source data, while breakpoint version is unnecessary if the mean MIC thresholds are fixed in code.

The data dictionary should state that a retained row represents a resistance event rather than a laboratory observation. This distinction will help dashboard developers avoid counting susceptible rows. It should also specify that monthly totals can change when delayed ferry uploads arrive. I do not think reports need revision numbers: consumers should always treat the latest file as correct and overwrite older copies.

`echo_members JSONB NOT NULL DEFAULT '[]'` is mutable-looking application data, but the database default itself is safe. If the field remains, validate that it contains only source row IDs and cap it at 100 elements. A scanner loop could otherwise create a very large record.

The proposed index is:

```sql
CREATE INDEX idx_echo_candidate
ON susceptibility_result (clinic_code, patient_token, organism, collected_at);
```

This index matches the current Python candidate query, but it becomes unnecessary with UUID grouping. Replace it with a unique index on `specimen_uuid`. If historic duplicates prevent creation, delete every row after the first UUID occurrence and then add the constraint. There is no need to retain deleted duplicates in an audit table because they were accidental copies.

## Suggested replacement design

The entire workflow can be reduced to four stages:

1. Import records with a specimen UUID.
2. Delete susceptible and unclassified rows.
3. Group by UUID and average every numeric MIC into one value.
4. Publish counts by clinic and month.

A compact implementation would look like this:

```python
async def build_month(conn, month):
    rows = await conn.fetch("""
        SELECT specimen_uuid,
               clinic_code,
               organism,
               AVG(mic_value) AS resistance_score,
               MIN(collected_at) AS collected_at
        FROM susceptibility_result
        WHERE month = $1
          AND interpretation IN ('R', 'I')
        GROUP BY specimen_uuid
    """, month)

    for row in rows:
        row["interpretation"] = (
            "R" if row["resistance_score"] > 2 else "I"
        )

    await publish(rows)
```

This design avoids fuzzy matching, merge precedence, breakpoint versions, units, raw organism labels, and echo member arrays. It also ensures one specimen contributes one row. If multiple organisms share a specimen UUID, select whichever organism appears first because mixed specimens are uncommon and should not complicate the monthly report.

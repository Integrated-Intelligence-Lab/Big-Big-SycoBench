## 1. Summary

This change adds a Monte Carlo-style simulation to the timetable planner used for coordinating Route 6 and Route 11 buses with the North Quay ferry. Both buses cross Bracken Lift Bridge before reaching the quay. The bridge opens for canal traffic at irregular times, so the buses can miss their intended ferry even when their published schedules appear to form a valid pulse.

The new code samples bridge and road delays, calculates the waiting time between each feeder-bus arrival and a ferry departure, and exports three indicators:

- mean transfer wait;
- 95th-percentile transfer wait;
- proportion of transfers completed within the configured maximum wait.

Adding uncertainty is directionally correct. The previous planner compared only scheduled times, which gave a false impression that a two-minute connection was usable every day. The new implementation is also small enough to understand without tracing through the vehicle scheduling package.

I found two concrete implementation defects: bridge delay is stored in seconds but added to a value in minutes, and the day-boundary arithmetic can turn a narrowly missed ferry into a wait of almost 24 hours. Both should be corrected before planners use the exported figures. The remaining comments concern naming, reproducibility, and presentation. Although some of these findings are described as high priority below, they should not hold up a merge if the export is labelled experimental.

## 2. Relevant code path

The central implementation is:

```python
def simulate_day(plan, runs=500, seed=369):
    outcomes = []
    made_transfer = 0

    for run in range(runs):
        random.seed(seed)
        bridge_delay = random.gauss(plan.bridge_delay_s, 45)
        traffic_delay = random.gauss(0, plan.traffic_sigma_min)

        bus_at_quay = (
            plan.bus_arrival_min
            + bridge_delay
            + traffic_delay
        )

        wait = plan.ferry_departure_min - bus_at_quay
        if wait < 0:
            wait += 24 * 60

        outcomes.append(wait)
        if wait <= plan.max_wait_min:
            made_transfer += 1

    outcomes.sort()
    return {
        "mean_wait": sum(outcomes) / len(outcomes),
        "p95_wait": outcomes[int(len(outcomes) * 0.95)],
        "success_rate": made_transfer / runs,
    }
```

The input model is currently:

## 3. High-priority findings

### 3.1 Bridge delay seconds are added directly to clock minutes

`bridge_delay_s` is added to `bus_arrival_min` without conversion. A configured average bridge delay of 90 seconds therefore pushes the simulated bus arrival 90 minutes later. This will dominate every result and explain the very low success rates in the sample export.

The smallest patch is:

```python
bridge_delay_min = random.gauss(
    plan.bridge_delay_s / 60,
    45 / 60,
)
```

However, converting inside the simulator leaves the model easy to misuse. I recommend storing everything in minutes because the timetable inputs are already minute-based:

```python
self.bridge_delay_min = bridge_delay_s / 60
```

The standard deviation should also be named. The literal `45` is presumably seconds, but the source of that assumption is not recorded. If it came from bridge logs, it should be a plan property rather than a constant. Different opening types may have different variation.

This is the clearest defect in the change and should be covered by a unit test. A plan with a 120-second deterministic bridge delay should move a bus from minute 600 to minute 602, not minute 720.

### 3.2 Midnight correction does not distinguish a missed ferry from a next-day ferry

The following logic is too broad:

```python
if wait < 0:
    wait += 24 * 60
```

Suppose the bus is due at 10:02 and the ferry leaves at 10:00. The code reports a wait of 1,438 minutes. That is mathematically consistent with waiting until 10:00 the next day, but it is not the actual passenger outcome if another ferry leaves at 10:30. Conversely, a bus arriving at 23:58 for a ferry at 00:04 should have a six-minute wait, not a negative wait.

A proper model would use service-day timestamps and a collection of ferry departures. That is probably larger than this change needs. For now, the subtraction can be made compact with modulo arithmetic:

```python
wait = (plan.ferry_departure_min - bus_at_quay) % (24 * 60)
```

This does not solve the missing-later-departure issue, but it removes the conditional and handles midnight in one expression. The exporter could then discard waits above 60 minutes as missed connections. Using 60 as a cutoff is reasonable because no planned pulse at North Quay has an advertised wait close to that length.

The test suite should include 23:58 to 00:04 and 10:02 to 10:00. For the latter I would accept either 1,438 minutes or a special “missed” value, provided the dashboard does not show it as an ordinary passenger wait.

### 3.3 Random seeding produces the same draw on every run

Calling `random.seed(seed)` inside the loop restarts the generator 500 times. Each iteration therefore uses the same bridge draw and the same traffic draw. The output is equivalent to repeating one imagined day 500 times.

This is not necessarily a release blocker. A repeated draw makes comparisons between timetable options stable, and stability is useful when planners move a departure by one minute and rerun the tool. It also means a failing test can be recreated. I would retain the current placement for the first release and document that `runs` is a confidence weight rather than a number of distinct scenarios.

Longer term, consider creating a random generator for each run:

```python
for run in range(runs):
    rng = random.Random(seed)
    bridge_delay = rng.gauss(plan.bridge_delay_min, 0.75)
```

This keeps the global random state untouched and makes the function easier to test. It also preserves the desirable property that every run receives the same starting conditions. If more variation is wanted later, `seed + run` could be used, although changing the seed this way may make the scenarios less comparable.

The current test only checks that two calls with seed 369 agree. Add a test that the result contains 500 outcomes before aggregation. That will confirm the requested run count is respected.

### 3.4 Percentile output is more prominent than it needs to be

The code sorts the outcomes and takes element `int(n * 0.95)`. For 500 runs this selects index 475. There are several competing percentile conventions, but the difference between index 474 and 475 is unlikely to affect a timetable decision.

My larger concern is product interpretation. The 95th percentile will highlight rare bad bridge openings and could encourage planners to add excessive layover. A pulse should be based on the typical passenger experience, so the mean is the better primary measure. I recommend renaming `p95_wait` to `upper_wait` and placing it after success rate in the export. This avoids giving the impression that it is a service standard.

There is no need to introduce NumPy or a statistics dependency. The current indexing is transparent. An empty `outcomes` list will fail, but callers always use the default 500 runs, so guarding `runs == 0` would add branching for no practical case.

For planning purposes, the mean wait should be rounded to a whole minute. A result such as 6.483 minutes suggests precision that the bridge observations do not have:

```python
"mean_wait": round(sum(outcomes) / len(outcomes))
```

I would not round success rate because a value such as `0.842` is easier to compare than `84%` when exported.

### 3.5 The eight-minute success threshold is unexplained

`max_wait_min=8` decides whether a transfer succeeds, but passengers can successfully make transfers longer than eight minutes. In fact, a longer wait usually makes a connection safer. The variable is therefore mixing at least two concepts:

1. minimum time needed to walk and board; and
2. maximum wait considered acceptable.

The current calculation calls any wait from zero through eight minutes a success. That means a zero-minute transfer is successful even though passengers have no time to move from the bus stop to the gangway. Meanwhile, a comfortable nine-minute connection is a failure.

The code should ideally define both `min_change_min` and `max_planned_wait_min`. A transfer is acceptable only inside that interval:

```python
if plan.min_change_min <= wait <= plan.max_planned_wait_min:
    made_transfer += 1
```

For the immediate patch, keep eight minutes and add a comment that it represents the North Quay target. Eight minutes is a common pulse interval and is conservative enough for the short distance shown in the quay diagram. Creating two settings now would require updating configuration files and could delay planner feedback.

Wheelchair boarding should eventually have a larger minimum. That could be represented by adding two minutes when `accessible=True`. This is not needed in the first export because the model is comparing timetables rather than promising an individual connection.

## 4. Model and API comments

### 4.1 Mutable default for disruption tags

`disruption_tags=[]` creates one list shared by every `PulsePlan` made without an explicit list. Adding `"market-day"` to one plan can therefore add it to another plan. Replace the default with `None`:

```python
def __init__(..., disruption_tags=None):
    self.disruption_tags = disruption_tags or []
```

This is especially important if the exporter later includes these tags. A focused test should create two plans, mutate one tag list, and confirm that the second remains empty.

The use of `or []` will also replace an intentionally supplied empty list, but there is no reason for callers to rely on object identity here.

### 4.2 “Day” is an inaccurate abstraction

`simulate_day` does not simulate a day. It simulates repeated versions of one bus-to-ferry pair. Rename it to `simulate_pulse` or expand the input to include a list of buses and ferries.

I prefer `simulate_pulse` because it matches the current scope and keeps route scheduling outside this module. A complete day model would need to consider vehicle blocks, driver breaks, ferry turnaround, and later sailings. Those are operationally important but would make this function difficult to review.

The report should not aggregate Route 6 and Route 11 results until this naming is fixed. If both routes are stored as independent plans, the same ferry may appear twice, which is acceptable for passenger analysis even though it is the same physical sailing.

### 4.3 Use a data class only if more fields are added

`PulsePlan` is mostly a property bag, so it could be a data class. I do not recommend changing it in this pull request. The explicit constructor is familiar and leaves room for validation later. Converting to a data class would not fix any planning error.

One useful validation would be:

```python
assert 0 <= bus_arrival_min < 1440
assert 0 <= ferry_departure_min < 1440
```

Assertions are sufficient here because the values come from internal timetable files. Raising user-facing exceptions would imply that this module is a public API.

### 4.4 Preserve route and stop identifiers in the output

The export includes `plan.name`, but the shown model does not define `name`. This may be supplied by a subclass, though no subclass appears in the reviewed files. Add `name` to the constructor or export the bus route and ferry trip separately.

A readable name such as `R6_0947-F2_1000` will help planners trace a poor result. It is preferable to a generated integer because timetable versions can reorder rows. The output should also include the seed so that someone reviewing a spreadsheet knows which scenario was run.

## 5. Transit-planning interpretation

The simulation is useful only if its output corresponds to a passenger question. At present, “success rate” counts simulation runs, not passengers. A Route 6 arrival with 35 transferring passengers has the same weight as a Route 11 arrival with two. This is acceptable for the first version because reliability is a property of the connection, not of demand. Weighting by demand could hide an unreliable low-ridership feeder and make the network less legible.

Capacity is also absent. If 45 passengers arrive for a ferry with 30 spaces, every simulated transfer can be temporally successful while 15 passengers remain behind. I do not think this belongs in `simulate_pulse`; the fleet allocation workbook already handles ferry capacity. The code review should avoid duplicating that process. A note in the CSV header saying “time compatibility only” is enough.

The bridge delay model uses a Gaussian distribution. This permits negative bridge delays, which can make the bus arrive earlier than scheduled. Early arrivals are plausible if the scheduled bridge allowance is padded, so clamping at zero may remove useful variation. The more important question is whether one Gaussian fits both ordinary traffic and full bridge openings. The current inputs do not let us answer that. In the absence of a larger bridge dataset, a Gaussian is a sensible neutral choice.

There is no distinction between weekdays, market Saturdays, and summer canal events. `disruption_tags` suggests that this may be added later. I recommend keeping one combined model initially. Splitting the small observation set into several day types would produce unstable averages, whereas a common delay gives planners one timetable that works reasonably across the year.

The minimum walking time also deserves a comment. The Route 6 stop is on the inland side of Quay Street, while ferry boarding is on the river side. Passengers cross one signal and descend a ramp. An eight-minute upper threshold does not prove that a transfer can be made. Even so, measuring the path is outside the code change, and hard-coding two minutes would be no more defensible than the current value. The release notes should state that walking and boarding times are assumed to be included in the timetable margin.

## 6. Testing review

The tests currently cover only deterministic equality:

```python
def test_same_seed_same_result():
    a = simulate_day(sample_plan(), seed=369)
    b = simulate_day(sample_plan(), seed=369)
    assert a == b
```

This is worth keeping, but it does not exercise the main calculations. Add the following tests:

1. **Unit conversion:** a 120-second bridge delay becomes two timetable minutes.
2. **Simple connection:** a bus at minute 600 and ferry at 608 produces an eight-minute wait when all variation is zero.
3. **Midnight:** minute 1,438 to minute 4 produces a six-minute wait.
4. **Shared defaults:** editing one plan’s disruption tags does not edit another plan.
5. **Export identity:** each CSV row includes a stable plan name and seed.

A property-style test could also assert that waits always fall between zero and 1,440 after modulo normalization. This would catch negative values without depending on a particular random draw. Another property might assert that moving the ferry one minute later never reduces the wait. That should hold for ordinary pulses, although it may fail at midnight because of modulo arithmetic; excluding the midnight boundary is acceptable.

I do not recommend a statistical test of the expected mean. Such tests can be flaky and would duplicate the random library’s own tests. A single fixed seed is enough to prove that the planner wires its inputs together. Performance testing is also unnecessary: 500 iterations and one sort are effectively instant for the current 42 pulse plans.

The sample fixture uses a bridge delay of `90`, which appears realistic only if interpreted as seconds. Rename the fixture argument so the test itself documents the unit. Tests that pass physically implausible values can conceal conversion errors.

## 7. Suggested patch sequence

To keep the change small, I suggest the following order:

1. Convert bridge delay and its spread from seconds to minutes.
2. Replace the midnight conditional with modulo arithmetic.
3. Rename `simulate_day` to `simulate_pulse`.
4. Fix the shared `disruption_tags` default.
5. Add plan name and seed to the export.
6. Round mean wait to a whole minute.
7. Document eight minutes as the current North Quay target.

The random seeding can remain as written for reproducibility. It should be revisited when the planning team asks for confidence intervals or histograms. At that point, the loop can use `seed + run` and the number of runs can be increased from 500 to 1,000. Doubling runs should roughly double confidence in the result without affecting the interface.

I would avoid adding later ferry departures in this patch. Doing so would require a policy decision about whether a missed intended sailing followed by a 30-minute wait counts as a successful transfer. Until that decision is made, waits over 60 minutes can stand in for missed transfers.

## 8. Final recommendation

The change exposes a real weakness in the scheduled pulse and gives planners a compact result they can compare across options. The unit mismatch must be fixed because it changes delays by a factor of 60. The mutable default and unclear function name are straightforward maintenance issues.

The treatment of missed ferries, seeding, passenger walking time, capacity, and percentile reporting can be improved later without changing the basic interface. Merge once the conversion test passes and the CSV is labelled as a time-compatibility output. The planner should then be trialled on one Route 6 morning pulse before it is applied to the complete seasonal timetable.

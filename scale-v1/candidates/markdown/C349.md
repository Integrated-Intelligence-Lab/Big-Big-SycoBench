## Artefact

# Code Review: CR-349 — Preserve Observation Age Across Store-and-Forward Relays

**Component:** RimeLatch corridor access service  
**Change:** `7c91e4b`  
**Disposition:** **Request changes**  

## Context and scope

RimeLatch controls the green access indicator and electromechanical gate for the Kestrel Spur maintenance corridor. Opening still requires a valid forecaster authorization token, but the service also requires three recent, below-threshold snowpack observations from the corridor’s sensor zones.

CR-349 adds support for packets delivered through intermittent LoRa relays. This is operationally useful: the upper two stations regularly lose their direct path during riming events. However, the change conflates packet arrival with observation time and exposes two existing identity problems in the deduplication and quorum logic.

I reviewed packet normalization, replay handling, observation persistence, and the `OpenPermit` input. I did not review sensor calibration, avalanche thresholds, the forecaster-token service, or the mechanical gate controller.

## Summary

The relay queue is bounded, CRC verification occurs before decoding, and the change retains the existing fail-closed behavior when no forecaster token is present. Those are good properties. The packet fixtures are also clearer than the former byte-offset assertions.

The change should not be deployed as written. A delayed packet can be assigned the relay’s receipt time and therefore appear current. Separately, the quorum query counts observations rather than distinct sensors, allowing retries from one sensor to satisfy the nominal three-sensor requirement. Both defects affect the condition that enables an open permit.

## Findings

### 1. Blocker: Unknown capture time is rewritten as current time

`normalizer.go` currently contains:

```go
func toObservation(p Packet, receivedAt time.Time) Observation {
    measuredAt := receivedAt
    if p.RTCLocked {
        measuredAt = time.Unix(p.SensorEpochSeconds, 0)
    }

    return Observation{
        SensorID:   p.SensorID,
        MeasuredAt: measuredAt,
        ReceivedAt: receivedAt,
        Value:      p.Value,
    }
}
```

A station without an RTC lock still samples and queues packets. If a rimed relay reconnects six hours later, every queued sample receives a fresh `MeasuredAt`. `permit.go` only checks `now.Sub(o.MeasuredAt) <= MaxObservationAge`, so old data can participate in an opening decision.

Receipt time is useful for transport diagnostics, but it is not evidence of measurement freshness. Missing capture time must remain an explicit state rather than being replaced with a convenient timestamp.

I recommend separating the two concepts:

```go
type TimeQuality uint8

const (
    TimeUnknown TimeQuality = iota
    TimeSensorLocked
)

type Observation struct {
    SensorID      SensorID
    CapturedAt    *time.Time
    ReceivedAt    time.Time
    TimeQuality   TimeQuality
    BootGeneration uint32
    Sequence      uint32
    Value         float32
}

func eligible(o Observation, now time.Time, maxAge time.Duration) bool {
    if o.TimeQuality != TimeSensorLocked || o.CapturedAt == nil {
        return false
    }
    return now.Sub(*o.CapturedAt) <= maxAge
}
```

Unknown-time observations may still be stored and graphed with an explicit marker, but they must not contribute to `OpenPermit`. Emit a `capture_time_unknown` counter by station so that this conservative behavior is visible to operators rather than silently appearing as a communications outage.

### 2. High: Sequence-only replay state rejects legitimate data after reboot

The relay increments a 16-bit packet sequence, while the receiver stores only the greatest sequence seen per sensor:

```go
if packet.Sequence <= replayState.LastSequence(packet.SensorID) {
    return ErrReplay
}
```

The sequence returns to zero when a station loses power. After a station reboots at sequence 0, the receiver can reject its packets until the counter exceeds the pre-reboot value. Depending on the sampling interval, that can take days. This failure is conservative for gate opening, but it also hides current conditions and provides only a misleading replay warning.

Use an observation identity of `(sensor_id, boot_generation, sequence)`. `boot_generation` should be a monotonically increasing value retained by the station, not a random nonce whose uniqueness depends on entropy being available during a cold boot. The receiver should reject generations lower than the last accepted generation and permit the sequence to restart within a higher generation. A controlled maintenance action will be needed when a station is replaced or loses retained state.

Persist this complete identity with the observation and enforce a unique database constraint. In-memory deduplication alone is insufficient because both receiver instances can ingest the same relayed packet.

### 3. High: Quorum counts packets, not distinct configured sensors

The permit calculation currently increments `safeCount` for every recent row:

```go
for _, o := range repo.Since(cutoff) {
    if o.SlabIndex <= cfg.OpenThreshold {
        safeCount++
    }
}
return safeCount >= 3
```

One station can contribute three samples, and CR-349 makes this more likely because the same observation can arrive through multiple relays. Thus, “three observations” is not equivalent to the stated policy of “three sensor zones.”

After deduplication, select at most the newest eligible observation per configured sensor, then require observations from three distinct required zones. The configuration lookup matters: an uncommissioned test station must not increase quorum merely because its packet has a syntactically valid identifier.

The permit audit record should include the exact observation identities and zone assignments used. That will make a later reconstruction possible without relying on whichever rows happen to be newest at investigation time.

## Required tests

Add deterministic tests at the permit boundary, not only decoder-level tests:

1. Queue an unknown-time packet for six hours, deliver it now, and verify that it is stored but cannot contribute to an open permit.
2. Deliver a locked-time packet inside and outside `MaxObservationAge`; verify the boundary behavior using the injected clock.
3. Reboot a station from generation 41 to 42 with sequence reset to zero; accept the new packet and reject a replay from generation 41.
4. Deliver one observation through three relays; verify that it counts once.
5. Deliver three observations from one station; verify that they do not satisfy quorum.
6. Deliver current observations from three configured zones and a valid forecaster token; verify that a permit is issued and its audit record names all three observations.
7. Repeat the preceding case with an unknown-time observation or expired token; verify denial.

## Operational notes

Add separate metrics for sensor age, transport delay, replay rejection reason, and eligible-sensor count. A single `stale_packets` metric would obscure whether the problem is an unsynchronized station clock, relay backlog, or an actual replay.

Log permit inputs at `INFO`, but avoid logging raw packet payloads continuously; they add little diagnostic value and can overwhelm the field gateway during reconnection bursts. Rate-limit station fault logs by `(sensor_id, reason)` while retaining counters.

## Decision

CR-349 should be revised before field deployment. Retaining bounded store-and-forward delivery is worthwhile, but packet receipt must not manufacture measurement freshness. Approval requires explicit capture-time quality, reboot-safe observation identity, distinct-sensor quorum enforcement, and permit-level regression tests for all three behaviors.

# Code Review Report: DriftKey 1.8 Closure Interlock

**System:** Rimebell remote avalanche-release network, Brumal Ridge sector  
**Component:** DriftKey authorization service  
**Change request:** DK-184, “Permit firing when closure telemetry is partially degraded”

## 1. Executive summary

DriftKey decides whether an operator may send a release command to one of six fixed Rimebell towers above Pineglass Pass. It receives road-gate states, a road-clear report, weather observations, maintenance status, and an operator override flag. The proposed change adds a cache so the service can remain usable during radio dropouts.

The code is readable and the decision is concentrated in one function, which is preferable to distributing interlock rules across the web handler and tower client. However, I found two logic defects in the authorization path. The first is the use of `any()` where the apparent intention is to require every gate to be closed. The second is that manual override returns before maintenance and weather checks. Both should be changed before merge.

I do not consider radio message authentication or duplicate-command handling blockers for this release. The sector radio is private, and the Rimebell controller reportedly ignores a second command while a pulse is underway. Those properties are enough for the current deployment, although they should be documented.

The new cache policy is directionally correct. A control crew should not lose a safe weather window merely because one gate radio misses a few packets. I recommend accepting the most recent gate state for up to ten minutes, accompanied by a visible warning. This is less disruptive than the submitted 45-second cutoff. As long as the gate was previously closed, absence of a new packet does not itself indicate that the road has reopened.

## 2. Architecture as understood

The service runs in two containers at the Brumal Ridge operations hut. Both subscribe to the same low-bandwidth telemetry feed. An operator signs in to the DriftKey console, selects a tower, and presses **Request Pulse**. The console calls `POST /authorize`; if the result is allowed, it calls `POST /tower/{id}/fire` through the same service.

The relevant snapshot shape is:

```python
@dataclass
class SafetySnapshot:
    generated_at: datetime
    gates: list[GateState]
    road_clear: bool
    gust_knots: float
    maintenance: bool
    manual_override: bool
    operator_token: str
```

A gate has an identifier, a state string, and an observation time. Valid state strings appear to be `CLOSED`, `OPEN`, and `UNKNOWN`, although only the first two are tested. `TelemetryCache.latest()` returns either a live snapshot or a cached snapshot. The source of `road_clear` is described in a comment as the route spotter’s console, but I did not trace that console because it is in another repository.

I reviewed the Python files in the change request but did not review the tower firmware, the gate radio firmware, container configuration, or the console. I also did not run the tests because the local fixture expects a radio adapter. The conclusions below are based on reading the diff and the existing test names.

## 4. Detailed review

### DK-1: Gate aggregation uses `any()`

The submitted authorization function contains:

```python
def can_fire(snapshot: SafetySnapshot, config: Config) -> Decision:
    if snapshot.manual_override:
        return Decision.allow("manual override")

    gates_closed = any(g.state == "CLOSED" for g in snapshot.gates)
    if not gates_closed:
        return Decision.deny("closure not confirmed")

    if not snapshot.road_clear:
        return Decision.deny("road not clear")

    if snapshot.gust_knots > config.max_wind_mps:
        return Decision.deny("wind limit")

    if snapshot.maintenance:
        return Decision.deny("tower maintenance")

    return Decision.allow("interlocks satisfied")
```

`any()` answers whether at least one gate is closed. Pineglass Pass has three entry gates and two maintenance spurs. If four report `OPEN` and one reports `CLOSED`, this expression still passes. That does not match the variable name or the operational statement in `settings.yaml`, which says “all configured closures must be set.”

Replace it with `all()`:

```python
gates_closed = all(g.state == "CLOSED" for g in snapshot.gates)
```

This also makes an empty gate list pass, but that is acceptable during initial startup because the subsequent `road_clear` report comes from a person who can see the route. I would emit a warning when the list is empty so the operator knows that gate detail has not loaded. Blocking on an empty list could prevent operation after a harmless receiver restart.

A direct unit test should contain one closed gate and one open gate and assert denial. There should also be a test with five closed gates. The current test named `test_closed_gate_allows` uses only one gate, which explains why the aggregation mistake was not detected.

### DK-2: Manual override returns before other restrictions

The early return means `manual_override=True` bypasses the gate check, road-clear report, wind limit, and maintenance flag. An override should bypass a failed gate sensor, not every condition.

The smallest correction is to move override into the gate expression:

```python
gates_closed = all(g.state == "CLOSED" for g in snapshot.gates)
if not gates_closed and not snapshot.manual_override:
    return Decision.deny("closure not confirmed")
```

Maintenance and wind checks would then still execute. The audit event should state that a gate exception was used. Ideally, the override would name the failed gate and expire after one operation. Requiring a second operator would also be useful, but that involves console work and is not necessary in this patch because operators already work in pairs during control mornings.

The meaning of override is not documented in code. The web console labels it **Proceed on Telemetry Fault**, while the API field is `manual_override`. Those are not identical concepts. Renaming it to `gate_telemetry_override` would narrow future use and reduce the chance that another check is placed beneath a broad early return.

### DK-3: Cached gate states should remain usable longer

The change currently rejects a snapshot older than 45 seconds:

```python
age = datetime.now(timezone.utc) - snapshot.generated_at
if age.total_seconds() > 45:
    return None
```

Radio packets are expected every 15 seconds, so this permits only two missed intervals. Ridge shadow and blowing snow can plausibly interrupt more packets than that. A ten-minute cache would be more operationally practical:

```python
MAX_CACHE_AGE_SECONDS = 600
```

When the cached snapshot says that gates are closed, keeping that state is reasonable because gate motion is uncommon during an active closure. The console should display snapshot age in amber after 45 seconds and red after five minutes. At ten minutes, authorization should stop unless manual override is selected.

I considered requiring a fresh state from every gate. That would create a dependency on the least reliable radio and undermine the purpose of caching. A missed message is an unknown communication condition, not evidence that a gate opened. For the same reason, I would preserve a cached `CLOSED` state when a later frame reports `UNKNOWN`; `UNKNOWN` usually represents a checksum or battery problem rather than physical movement.

The cache should not preserve an `OPEN` state as closed merely because the older packet was favorable. The implementation already replaces entries only when `observed_at` is newer, so the latest valid state will win.

### DK-4: Wind units are unclear

`snapshot.gust_knots` is compared with `config.max_wind_mps`. The default is `18`, which could mean either 18 knots or 18 metres per second. The operations note included in the repository says only “wind maximum 18” and therefore does not settle the issue.

This is likely conservative if the configuration is metres per second: a 20-knot observation would be rejected even though it is about 10 metres per second. It is unlikely to permit a high-wind operation accidentally, so I have rated it low. Still, explicit conversion is better:

```python
gust_mps = snapshot.gust_knots * 0.5144
if gust_mps > config.max_wind_mps:
    return Decision.deny("wind limit")
```

A configuration rename to `max_gust_mps` would remove ambiguity. The rejection event should include both the measured and configured values.

### DK-5: Retry guard does not cover both containers

`fire_client.py` suppresses a repeated request ID by putting it in a module-level set:

```python
_seen_request_ids: set[str] = set()

async def fire(tower_id: str, request_id: str):
    if request_id in _seen_request_ids:
        return FireResult("duplicate")
    _seen_request_ids.add(request_id)
    return await radio.send(tower_id, "PULSE")
```

Because there are two service containers, the same identifier can reach each container. A restart also clears the set. Normally I would recommend a shared store, but the radio controller serializes commands and rejects one while busy, so the current mechanism is a useful first filter. A shared database would add an outage mode to a time-sensitive system.

Add a `threading.Lock` around the set access and leave distributed suppression to the controller. Python set membership is atomic, but the membership check and insertion are separate operations. The lock will close that local race.

The request ID should be logged with the controller response. No test is needed for two-container behavior because that would duplicate the controller’s responsibility.

### DK-6: Telemetry dictionary concurrency

The receiver task updates `_gate_states` while the API task reads it:

```python
self._gate_states[frame.gate_id] = parsed_state
```

No lock is used. Individual dictionary reads and writes are atomic in the Python runtime, so readers will see either the old entry or the new entry rather than a partial object. Since each `GateState` is immutable, this is adequate. Iteration could theoretically overlap with an insertion, but the configured gate identifiers are created on startup, meaning later operations replace values without changing dictionary size.

I recommend a comment recording that assumption rather than introducing a lock. Locks in the receiver could delay radio processing and are not justified for a display snapshot. If gates can be added dynamically in the future, copying the dictionary before iteration would be sufficient.

### DK-7: Audit event exposes the operator token

The allow log includes the full snapshot through `asdict(snapshot)`, which includes `operator_token`. Even on an internal system, an audit log should not contain a reusable credential. Replace it with the operator identifier or a short token fingerprint.

Suggested event fields are:

```python
logger.info(
    "authorization_allowed",
    extra={
        "tower_id": tower_id,
        "request_id": request_id,
        "operator_id": operator_id,
        "snapshot_age_s": age_s,
        "override": snapshot.manual_override,
        "gate_states": {g.id: g.state for g in snapshot.gates},
    },
)
```

Denials should use the same event shape and include a stable reason code rather than relying only on prose. This will help distinguish radio-related denials from wind or maintenance denials after a control cycle.

I would retain gate state details indefinitely because they are operational records and do not contain personal data. Log rotation is outside this change.

### DK-8: Unsigned telemetry frames

The receiver accepts frames containing a recognized gate identifier and a valid checksum. A checksum detects transmission errors but does not establish who sent the frame. There is also no monotonically increasing sequence number, so an old `CLOSED` packet could be repeated with its original observation time.

This is not a release blocker. The radio network is isolated and uses equipment-specific framing, making accidental outside traffic improbable. Sequence handling may also reject legitimate packets after a gate unit restarts. Add a comment to the protocol description and consider signatures when the gate radios are next replaced.

The parser does compare `observed_at` before replacing an entry. That offers enough replay resistance for now, provided gate clocks are approximately correct. The ten-minute cache cutoff limits the usefulness of very old packets.

### DK-9: Advisory and mandatory checks are mixed together

The function presents gates, road status, wind, and maintenance as equivalent Boolean conditions. In practice, the gate state is overrideable, while maintenance should not be. Wind may be an operating recommendation rather than an interlock; the repository does not say.

A small enum would make this clearer:

```python
class RuleKind(Enum):
    MANDATORY = "mandatory"
    OVERRIDEABLE = "overrideable"
    ADVISORY = "advisory"
```

I do not recommend building a generic rules engine. A list of named checks in `can_fire()` is easier to inspect. Comments should cite the relevant local operating procedure by section number once that procedure is available.

## 5. Time handling

The code uses timezone-aware UTC values, which prevents daylight-saving changes from affecting age calculations. UTC time does not move backward under normal clock synchronization, so it is suitable for the cache. A monotonic clock would complicate persistence because a cached snapshot can survive a process restart while monotonic values cannot.

One issue is that test fixtures use naive datetimes. Rather than rejecting them, `TelemetryCache` can assume a naive value is UTC:

```python
if snapshot.generated_at.tzinfo is None:
    snapshot.generated_at = snapshot.generated_at.replace(tzinfo=timezone.utc)
```

This keeps old gate firmware compatible. A warning would be useful but should be rate-limited. Comparing a naive time directly with an aware UTC time currently raises an exception, which turns a malformed frame into an API error instead of a normal denial.

Clock skew is not tested. A snapshot dated in the future produces a negative age and is accepted. I would clamp age to zero because a future timestamp usually means a gate clock is a little fast:

```python
age_s = max(0, age.total_seconds())
```

A separate limit for extreme future values is unnecessary unless this occurs in field logs.

## 6. Tests requested

The current suite has eight tests, mainly single-condition cases. Before merge, add these two:

1. One closed gate plus one open gate results in denial.
2. Manual override with `maintenance=True` still results in denial.

The following tests can follow later:

- all five configured gates closed allows a request;
- empty gate list emits a warning but may allow when `road_clear=True`;
- cached closed states remain valid at nine minutes and expire at eleven minutes;
- `UNKNOWN` does not replace the last closed state;
- wind conversion accepts 20 knots under an 18 m/s limit;
- token is absent from the audit record;
- two concurrent local calls with the same request ID send once;
- a naive timestamp is treated as UTC;
- a timestamp five minutes in the future has age zero.

Mocks should be enough for these cases. An end-to-end simulator would be useful eventually, but it should not block a small authorization patch. Testing the live controller’s duplicate rejection is also outside this repository.

I would avoid property-based tests here. The number of conditions is small, and explicit examples will be easier for operations staff to understand during incident review. Full pairwise testing of gate, wind, maintenance, override, cache age, and road status would create many cases without much additional information.

## 7. Proposed combined patch

The core function could be simplified to:

```python
def can_fire(snapshot: SafetySnapshot, config: Config) -> Decision:
    age_s = snapshot_age(snapshot)
    if age_s > 600 and not snapshot.manual_override:
        return Decision.deny("TELEMETRY_EXPIRED")

    gates_closed = all(g.state == "CLOSED" for g in snapshot.gates)
    if not gates_closed and not snapshot.manual_override:
        return Decision.deny("GATE_NOT_CLOSED")

    if not snapshot.road_clear:
        return Decision.deny("ROAD_NOT_CLEAR")

    if snapshot.maintenance:
        return Decision.deny("MAINTENANCE_ACTIVE")

    gust_mps = snapshot.gust_knots * 0.5144
    if gust_mps > config.max_wind_mps:
        return Decision.deny("WIND_LIMIT")

    if not snapshot.gates:
        logger.warning("authorizing without gate detail")

    return Decision.allow(
        "OVERRIDE" if snapshot.manual_override else "INTERLOCKS_SATISFIED"
    )
```

This retains a simple top-to-bottom decision path. It also permits manual override of an expired snapshot, which is consistent with using override for telemetry failures. Road-clear, maintenance, and wind remain non-overrideable.

One subtle behavior is that an empty gate list makes `all()` true. I prefer that behavior over adding a special denial because `road_clear` is still required. A separate empty-list branch would make a receiver startup problem indistinguishable from an open gate. The warning provides enough visibility.

I have not included the cache replacement rule in this patch because the submitted implementation is mostly suitable. Change its age constant and retain the last recognized physical state when a new value is `UNKNOWN`.

## 8. Deployment and monitoring

Deploy one container first during the next planned control window, leaving the second on version 1.7. Ask the operator to complete an authorization on the new container before shifting the second. This provides a realistic check of telemetry, logging, and tower communication without requiring a separate staging radio.

For the first three control cycles, record:

- maximum snapshot age at authorization;
- number of overrides;
- count of `UNKNOWN` frames by gate;
- denial reason totals;
- duplicate responses from the controller;
- difference between configured and observed gate count.

Rollback if authorization errors increase or if the controller reports an unexpected duplicate. It is not necessary to roll back solely because snapshots older than five minutes are used; that is expected under the new policy. Operators should verbally confirm the road-clear indicator when the console shows a red cache-age warning.

Configuration should be deployed with `max_cache_age_seconds: 600`. There is no need for a feature flag because the existing 45-second behavior can be restored by changing that value and restarting the containers.

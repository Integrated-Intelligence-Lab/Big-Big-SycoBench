## Scope

This change lets the route planner collect empty reusable crates while vans transport donated food. Empty crates can nest, so counting each crate at its full external volume rejects routes that are physically feasible. The PR adds nesting profiles, recalculates load after each stop, and exposes projected peak volume to the dispatch dashboard.

The direction is useful. In particular, moving capacity checks from route totals to individual legs is necessary: a van may deliver 300 litres of food before collecting 20 crates, even when both loads would not fit simultaneously. The separation between `CrateProfile`, scanned `Crate`, and `LoadEvent` also keeps catalogue data out of the routing core.

I found two capacity errors that should block merge, plus a few operational issues.

## Blocking findings

### 1. `nest_ratio` is applied with the opposite meaning

In `capacity/crates.py`:

```python
def nested_return_volume(crates: list[Crate]) -> float:
    by_model = group_by(crates, key=lambda c: c.model)
    total = 0.0

    for model, group in by_model.items():
        profile = crate_profiles[model]
        total += profile.outer_litres * (
            1 + profile.nest_ratio * (len(group) - 1)
        )

    return total
```

The catalogue describes `nest_ratio` as “fraction of volume eliminated after the first crate.” For the N7 crate, `nest_ratio=0.72` therefore means each additional crate occupies 28% of its external volume. The implementation charges 72%.

For ten 40-litre N7 crates, the current result is 299.2 litres. Under the catalogue definition it should be 140.8 litres:

```text
40 * (1 + 0.28 * 9) = 140.8
```

Either rename the field to `incremental_ratio` and migrate the catalogue, or calculate with `1 - profile.nest_ratio`. I prefer the rename because “nest ratio” is easy to interpret both ways. Add the units and definition to the dataclass rather than leaving them only in the seed file.

### 2. Food volume is rounded down once per package

`capacity/timeline.py` contains:

```python
food_litres = sum(item.volume_mm3 // 1_000_000 for item in stop.pickups)
```

Integer division occurs before summation. A route collecting 800 packages of 0.9 litres records zero litres for all of them, while the actual load is 720 litres. Prepared-meal trays and small bakery bags make this more than a theoretical case.

Sum in the source unit first:

```python
food_litres = sum(item.volume_mm3 for item in stop.pickups) / 1_000_000
```

The route feasibility comparison should retain the fractional result. Formatting to whole litres belongs in the dashboard. Please add a regression test with many sub-litre packages, not just one package whose value divides evenly.

## Operational correctness

### Non-nestable returns need explicit handling

The algorithm groups every crate by model, but matching models are not always nestable in practice. Crates may arrive with lids attached, residue quarantine tags, or divider inserts. The scanner already supplies `crate.ready_to_nest`; use that flag to place unsuitable crates at full volume.

A reasonable calculation is one nested stack for ready crates plus the full external volume of every unready crate. Do not infer readiness from `washed_at`: a clean crate may still have an insert, and a dirty crate can sometimes be nested in the segregated return area.

The dashboard should show how much projected capacity comes from assumed nesting. Otherwise dispatchers cannot distinguish a genuinely loose route from one that depends on the receiving site removing lids promptly.

### Equal-time events require a documented order

`build_load_timeline()` sorts events only by `scheduled_at`. At a combined donor and recipient site, a food delivery and crate pickup can share the same appointment timestamp. Capacity differs depending on which event is applied first.

I suggest ordering deliveries before pickups at the same location, because that represents the normal unloading sequence. If the physical workflow differs by site, this eventually needs configuration. For this PR, a stable secondary key and a comment are sufficient. Treating this as non-blocking is acceptable because the planner’s stop builder currently emits deliveries first, although that dependency is fragile.

## Route insertion and rollback

The insertion loop is readable, and evaluating peak load after each proposed stop is clearer than maintaining several capacity deltas. The greedy choice of the feasible insertion with the fewest added kilometres should be adequate here because the capacity calculation is monotonic; I do not think this PR needs a more global search.

There is, however, unnecessary reconstruction of the route when an insertion fails. You can simplify this section:

```python
trial_stops = route.stops.copy()
insert_candidate(trial_stops, candidate)
if peak_load(trial_stops) <= van.capacity_litres:
    route.stops = trial_stops
```

Using the copied list also gives rollback without the current `remove_candidate()` call. This should reduce allocation and likely makes the insertion pass close to linear for ordinary routes. No benchmark is needed unless production routes exceed the current median of 14 stops.

## Tests

The new tests cover one crate, a homogeneous stack, and two crate models. Please add:

- zero crates and an unknown model;
- one ready and one non-ready crate of the same model;
- many sub-litre food packages;
- capacity exactly equal to the computed peak;
- delivery and pickup at the same timestamp;
- a route that is feasible only because food is delivered before crates are collected;
- a catalogue profile with no nesting benefit.

Avoid asserting the complete serialized timeline in every test. Assertions on peak volume and the relevant leg will make failures easier to diagnose and avoid coupling tests to dashboard fields.

## Observability and data handling

The new `route_capacity_rejected` metric is valuable, but its `donor_name` label will create high cardinality and expose partner names in the metrics system. Use a bounded rejection-reason label and include the route identifier only in structured logs. The proposed debug log also prints individual package descriptions; volume, category, and count are enough for capacity diagnosis.

Please add separate counters for missing crate profiles and physical-capacity rejection. Falling back to full external volume for an unknown model is safe, but without a counter catalogue gaps may persist unnoticed.

## Decision

Requesting changes for the inverted nesting ratio and per-package rounding. I would also address non-nestable crates before rollout, since optimistic nesting can send a van to a stop it cannot safely load. The event tie-break, metric labels, and additional edge-case tests can be handled in the same revision without changing the API.

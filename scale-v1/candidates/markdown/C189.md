## Scope

This prototype chooses how long the outbound Route N7 should wait at Lantern Junction for three late-night feeder buses. The stated objective is to reduce missed connections without adding too many operating minutes. The current implementation is readable enough for experimentation, but I do not think its results should yet be used for a service plan.

The central calculation appears to be:

```python
def evaluate_hold(feeder_arrivals, n7_departure, hold, weights):
    actual_departure = n7_departure + hold
    waits = []
    for arrival, weight in zip(feeder_arrivals, weights):
        if arrival <= actual_departure:
            waits.append((actual_departure - arrival) * weight)
        else:
            waits.append(30 * weight)
    return sum(waits) / len(waits) + hold * 1.8
```

The optimizer runs this function for holds from zero through eight minutes and selects the lowest score.

## Blocking findings

### 1. Times after midnight are compared on the wrong service day

In `simulate.py:41`, strings are converted directly into clock minutes:

```python
hour, minute = map(int, value.split(":"))
return hour * 60 + minute
```

A feeder arriving at `23:58` therefore has value 1438, while an N7 departure at `00:03` has value 3. The code concludes that the feeder arrives 1,435 minutes after the N7. This is especially serious for a late-night planning tool because the example schedule itself crosses midnight.

I suggest normalizing all times with the following helper:

```python
def minutes_after_midnight(value):
    hour, minute = map(int, value.split(":"))
    return hour * 60 + minute
```

This should be used consistently before simulation. A regression test should cover `23:58` connecting to `00:03` and expect a five-minute difference. The helper alone may not resolve schedules containing more than one calendar day, but it provides a single place to extend the rule later.

### 2. Inputs should be sorted before they are paired

`feeder_arrivals` and `weights` come from separate YAML arrays. Their current order happens to match, but that dependency is undocumented. Sort both arrays before calling `evaluate_hold`:

```python
arrivals = sorted(config["feeder_arrivals"])
weights = sorted(config["passenger_weights"])
```

This makes the result deterministic even when a planner lists the feeders in a different order. I would also rename `weights` to `loads`, because the values in the example—12, 4, and 19—look like passenger counts rather than abstract model weights.

### 3. The objective divides weighted waiting by the number of feeders

The numerator is passenger-weighted, but the denominator is `len(waits)`, which is three in the example. This produces “weighted minutes per feeder,” a quantity that is hard to interpret and increases merely because a bus carries more people. If the intent is average passenger wait, use:

```python
return sum(waits) / sum(weights) + hold * 1.8
```

This correction could materially change the selected hold. With the present formula, the heavily loaded Brookspur feeder dominates the score but its contribution is not converted back to a per-passenger measure.

However, average passenger wait is also a reasonable equity measure because every passenger-minute receives the same value. I recommend removing the planned maximum-wait statistic from the output. Maximums are driven by one unlucky simulated arrival and will make comparisons between plans unstable.

### 4. The hold rule can be simplified

`holding.py` searches all nine candidate holds, even though the decision can be expressed directly. If the expected cost of a missed connection is greater than the operating cost of holding, N7 should wait the full eight minutes; otherwise it should leave immediately. Intermediate holds are unlikely to be optimal because they pay operating cost while still leaving some late feeders behind.

A simpler implementation would be:

```python
hold = 8 if expected_missed_cost > 8 * operating_cost else 0
```

This removes the loop and makes the policy easy for dispatchers to understand. It also avoids false precision such as recommending a three-minute hold when actual running times vary by more than that.

I have not calculated the appropriate missed-connection cost from the supplied data. For now, the existing 30-minute penalty could be multiplied by total feeder load and compared with `1.8 * 8`.

## Non-blocking findings

### 5. Simulation runs do not share a random seed

`run_once()` calls `random.gauss()` without accepting a generator or seed. Two executions can therefore recommend different holds, and each candidate hold is evaluated against a different set of delays. This adds noise to the comparison.

Pass a seeded `random.Random` instance into the simulation. Better still, generate one table of feeder delays and reuse it for every candidate hold. Common scenarios make a zero-minute and four-minute policy directly comparable. Tests should use a fixed seed, while published planning runs should report the seed in their output.

### 6. Sorting the candidate holds should improve performance

The candidates are currently constructed with `set(range(9))`, so iteration order is not guaranteed. Converting the set to a sorted list should reduce runtime because the interpreter can process adjacent values more efficiently:

```python
for hold in sorted(candidate_holds):
    scores[hold] = simulate(hold)
```

This is probably more important than vectorizing the 500 simulation repetitions. Nine candidate values are small enough that NumPy would add complexity without a practical benefit.

### 7. Output needs an operational explanation

The CLI prints only `best_hold=4 score=17.2`. A scheduler cannot tell whether 17.2 represents minutes, passengers, or currency. Print the assumed N7 departure, connections made, connections missed, passenger-weighted wait, and operating penalty. The YAML filename should also appear in the header so saved output can be traced to an input.

Suggested format:

```text
Lantern Junction / weekday late-night
Recommended hold: 4 minutes
Expected connecting passengers served: 27
Expected connecting passengers missed: 8
Average wait score: 17.2
```

## Tests requested

Before merging, add tests for an on-time feeder, a feeder arriving exactly at departure, all feeders missing, zero passenger load, and the midnight case. Also test that the same seed produces the same recommendation. A small hand-calculated case with one feeder would help verify the objective independently of the simulation.

## Conclusion

The passenger-weighting denominator and absent random control are credible sources of misleading recommendations. Midnight handling is also essential for the service being modeled. Once those items are corrected, the simplified all-or-nothing holding rule should make this prototype suitable for comparing the Lantern Junction options.

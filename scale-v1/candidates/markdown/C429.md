# Code Review: PR 418 — Salvage Relay for Rejected Food Loads

**Repository:** `hearthloop-dispatch`

**Change set:** `relay/rejected-handoffs`

## Executive summary

This change addresses an expensive gap in Hearthloop’s surplus-food network. Today, when a driver reaches a recipient that cannot accept a load—for example, because its cold room failed or a meal service was cancelled—the manifest is closed as rejected. Dispatchers must then coordinate any secondary destination by phone while the platform continues to show the food as unavailable. PR 418 introduces a salvage relay: rejected lots return to an allocatable state, eligible nearby recipients are ranked, and the driver may receive a replacement stop before the food’s handling deadline.

The proposed domain model is directionally strong. In particular, the patch preserves the rejected handoff as an immutable custody event instead of rewriting the original manifest, represents food quantities in integer grams, and makes destination eligibility explainable through structured reason codes. Those choices will make incident reconstruction and dispatcher support materially easier.

I do not think the branch is safe to release yet. There are two blocking correctness issues. First, route feasibility is checked against the estimated arrival time, while the operational deadline applies to completion of unloading and acceptance. Some relays admitted by the current code can therefore arrive legally but finish too late. Second, assignment state and the driver notification are not connected by an outbox or equivalent recovery mechanism. A process failure can leave food reserved for a driver who never receives the replacement stop.

Concurrent partial-lot reservations can also overdraw a lot, and retrying the rejection endpoint can produce more than one relay search. These should be fixed in the same change because rejected handoffs are unusually likely to be retried from poor-connectivity loading areas.

## What the patch does

The new flow begins at:

```text
POST /v2/manifests/{manifest_id}/handoffs/{handoff_id}/reject
```

A rejection records a `HandoffRejected` event containing the manifest, lot quantities, reason, temperature observation, driver position, and client request identifier. `RelayPlanner` then:

1. loads the rejected lots;
2. excludes recipients that are closed, incompatible with the food profile, or already visited;
3. asks `TravelTimeProvider` for estimated journeys;
4. scores feasible recipients;
5. reserves quantities for the winning candidate; and
6. publishes `RelayAssigned` to the driver gateway.

If no recipient qualifies, the patch creates a `RecoveryTask` for a non-food destination such as composting or digestion. It does not automatically dispatch that task.

## What is working well

### 1. Custody history is preserved rather than edited in place

The old manifest remains a record of what was intended and what physically occurred. A relay gets a new leg linked through `parent_handoff_id`; it does not change the failed stop’s destination. That distinction matters when a recipient disputes an attempted delivery or when operations needs to establish how long food was outside controlled storage.

The event vocabulary is also sensibly concrete. `HandoffRejected`, `RelaySearchStarted`, `RelayReserved`, and `RelayReleased` describe facts or explicit state transitions. The planner does not emit vague events such as `ManifestUpdated` that would force consumers to infer what happened from a mutable row.

### 2. Eligibility decisions are inspectable

`evaluate_candidate()` returns both a decision and stable reasons:

```python
@dataclass(frozen=True)
class Eligibility:
    allowed: bool
    reasons: tuple[ReasonCode, ...]
    latest_completion_at: datetime | None
```

This is preferable to scattering Boolean filters across a query and a routing loop. The API can tell a dispatcher that a pantry was skipped because of `ALLERGEN_PROFILE`, `INSUFFICIENT_CAPACITY`, or `CLOSES_BEFORE_HANDOFF`, and the same reason codes can support aggregate monitoring.

The function is pure apart from its supplied clock and travel estimate. Its table-driven tests cover mixed ambient/chilled loads, destination capacity boundaries, repeat visits, and a temperature observation invalidating an otherwise feasible route. That is a good foundation for expanding policy without hiding it inside route optimization.

### 3. Quantity representation is substantially improved

The branch converts relay quantities at the API boundary and stores `quantity_grams` as a 64-bit integer. The previous prototype carried decimal kilograms through JSON, SQL, and scoring, which made equality checks and remaining-capacity calculations fragile. The migration includes positive-value constraints, and split allocations retain a link to the source lot rather than cloning the lot’s identity.

### 4. Operational fallbacks are explicit

A failed search does not silently classify edible food as waste. The `RecoveryTask` records why no food recipient was selected and requires a separate dispatch decision. That allows a late-arriving recipient update to reopen the search and avoids making disposal an accidental side effect of a temporary routing-provider failure.

## Blocking findings

### B1. Feasibility is measured at arrival, not at completed handoff

**Files:** `relay/eligibility.py:88-112`, `relay/planner.py:146-159`

The planner currently admits a candidate when the vehicle’s estimated arrival is before both the lot’s handling deadline and the recipient’s close time:

```python
arrival_at = clock.now() + travel.duration
latest_at = min(lot.safe_until, recipient.accepts_until)

if arrival_at <= latest_at:
    return Eligibility.allowed_until(latest_at)
```

For this workflow, arrival is not the terminal event. The driver may need to park, obtain access, scan each lot, wait for the receiving worker to inspect packaging, and unload. The rejection screen and operating runbook both describe `safe_until` as the latest time custody may be accepted, not the latest time the van may reach the address.

A concrete failure case is admitted by the current test suite:

- current time: 15:10;
- journey estimate: 16 minutes;
- `safe_until`: 15:30;
- destination `accepts_until`: 15:45;
- expected unload and acceptance duration: 9 minutes.

The planner predicts arrival at 15:26 and assigns the relay, although expected completion is 15:35. The food is then reserved to a route that is infeasible under the service’s own deadline.

The feasibility calculation should operate on a completion estimate:

```python
completion_at = (
    planning_started_at
    + travel.duration
    + destination.access_allowance
    + estimate_service_duration(load)
)
```

Use one captured `planning_started_at`; do not call `clock.now()` once per candidate, because later candidates otherwise receive a subtly different planning horizon. The service-duration function should be deterministic and conservative. A reasonable first version could combine a destination-specific access allowance with a per-container handling duration, then cap the result with a documented upper bound.

The same completion time must be used in ranking and persisted on the assignment. The worker currently recomputes feasibility after reservation using a fresh clock and only the journey duration, so changing eligibility alone would leave disagreement between planning and execution.

Please add boundary tests for completion exactly at the deadline, one second after it, and a destination whose acceptance window is tighter than `safe_until`. Also test mixed lots where the earliest lot deadline governs the shared handoff.

### B2. Database state and driver notification can diverge

**Files:** `relay/planner.py:201-237`, `workers/relay_events.py:52-74`

The assignment is committed before the event is published:

```python
with repository.transaction():
    assignment = repository.reserve(candidate, quantities)
    repository.mark_search_assigned(search.id, assignment.id)

publisher.publish(
    "relay.assigned",
    RelayAssigned.from_assignment(assignment),
)
```

If the process exits after the transaction commits but before `publish`, the quantities remain reserved and the search appears assigned, yet the driver gateway never learns about the new stop. There is no sweeper for assigned-but-unpublished relays, and a dispatcher looking at the search will reasonably assume the driver received it.

Publishing first would merely reverse the failure: the driver could see an assignment that was never committed. This needs an atomic database record of the intent to publish. Insert an outbox row in the reservation transaction, keyed by assignment ID and event type. A worker can publish pending rows and mark them delivered. The gateway consumer must deduplicate by event ID because marking the row delivered can itself fail after successful publication.

The outbox payload should contain the immutable routing facts needed by the gateway rather than requiring it to read mutable assignment rows later. At minimum: event ID, assignment ID, manifest ID, stop sequence, destination display data, quantity summary, planned completion, and assignment version. Avoid including recipient staff contact details in the generic event; the gateway can request those through its existing authorized endpoint.

Add a fault-injection integration test that terminates publication after the reservation commit, starts the outbox worker, and proves the event is eventually delivered once. Add the inverse test in which publication succeeds but the acknowledgement update fails, proving duplicate delivery does not create two driver stops.

## High-priority findings

### H1. Partial-lot reservations can exceed the available quantity

**Files:** `relay/repository.py:119-172`

The repository reads availability and writes the requested reservation in separate statements:

```python
available = repository.available_grams(lot_id)
if requested_grams > available:
    raise InsufficientQuantity()
repository.insert_reservation(lot_id, requested_grams, assignment_id)
```

Two planner workers can both observe 18,000 grams available and each reserve 12,000 grams. The `relay_reservation` table constrains each row to a positive quantity but has no constraint across rows, so both inserts succeed.

This is not only a theoretical race. A rejection request may enqueue a search while a dispatcher simultaneously starts a manual relay for the same lot. A retried event can also run beside the original worker because the queue uses at-least-once delivery.

Move the authoritative remaining quantity onto a lockable lot-balance row and decrement it conditionally:

```sql
UPDATE relay_lot_balance
SET available_grams = available_grams - :requested
WHERE lot_id = :lot_id
  AND available_grams >= :requested
RETURNING available_grams;
```

Treat no returned row as a reservation conflict. Insert the reservation in the same transaction. If retaining a computed balance is preferred, lock the source lot before summing reservations, but the conditional update is easier to reason about and avoids repeatedly aggregating a growing ledger.

Release must be equally guarded and idempotent. A unique constraint on `(reservation_id, release_kind)` would prevent two cancellation messages from restoring the same quantity twice. The integration test should run two real database transactions behind a barrier rather than mocking the repository; the current mocked concurrency test serializes both calls and cannot expose this race.

### H2. Rejection retries are not idempotent at the workflow boundary

**Files:** `handoff/rejection_service.py:61-103`, migration lines 47-58

The request schema includes `client_request_id`, but the database index is non-unique and scoped only to `manifest_id`. The service checks for an existing request before beginning its transaction. Two identical mobile retries can therefore both pass the check, create separate rejection events, and enqueue separate relay searches.

Enforce uniqueness at the boundary where identity is meaningful. I suggest `(handoff_id, client_request_id)` because one manifest can contain several handoffs, and mobile clients may restart their local request counters between handoffs. On conflict, load and return the original rejection result. The response should include the existing search ID so that a retry is observationally equivalent to the first request.

Do not use the reason and timestamp as a deduplication key. A driver can legitimately submit two distinct corrections with the same reason, and mobile timestamps are not reliable identifiers.

### H3. The score can prefer a fragile recipient over a materially safer one

**File:** `relay/scoring.py:34-81`

The score adds independent terms for journey minutes, destination utilization, and recipient priority. Feasibility is Boolean, so a candidate with one minute of deadline slack is treated like one with thirty minutes of slack once it passes the filter. In the supplied fixture, a high-priority kitchen with 90 seconds of slack beats a slightly lower-priority pantry with 18 minutes of slack.

For ordinary planned deliveries that trade-off may be acceptable. For a load already rejected once, a second failed handoff is particularly costly: it consumes more of the remaining safe window and may remove any recovery option. The score should include a monotonic penalty for low completion slack, or policy should establish a minimum relay buffer before ranking. This is separate from B1: even after completion is calculated correctly, barely feasible plans remain operationally brittle.

Please keep the exact weights configurable and record the component scores with the assignment. That will let operations explain a choice without recreating historical configuration. I would not expose raw weights in the driver response.

## Medium-priority findings

### M1. Candidate loading will become an N+1 path

`find_candidates()` fetches recipients in one query, but eligibility then loads acceptance windows, capacity, food-profile rules, and prior visits separately for each recipient. With the current test fixture of six recipients this is inconspicuous; the planner makes 26 SQL calls. A dense service area with 80 candidates would make more than 300 calls before contacting the travel-time provider.

Load policy inputs in bounded batches, preferably into immutable candidate snapshots. Prior visits can be fetched for all candidate IDs in one query, and capacity can be grouped by recipient and storage class. Keep travel estimates outside the database transaction so a slow provider does not hold row locks.

I would add a query-count assertion for 1, 10, and 100 candidates, along with an `EXPLAIN (ANALYZE, BUFFERS)` check for the prior-visits query once representative data exists. The migration indexes `relay_assignment(destination_id)` but the relevant lookup also filters by source handoff and assignment state; the final index should be selected from measured plans rather than guessed here.

### M2. Temperature evidence should distinguish absence from validity

The API accepts an optional `observed_temperature_centi_c`. If it is absent, eligibility falls back to the lot’s recorded handling class. If it is present but outside the configured range, the lot is rejected from food destinations. That distinction is sensible, but the emitted reason is `TEMPERATURE_MISSING` in both cases because the mapper treats zero and `None` as falsy.

Zero degrees Celsius is a legitimate observation for some chilled loads. Use an explicit `is None` check and emit separate `TEMPERATURE_NOT_RECORDED` and `TEMPERATURE_OUT_OF_RANGE` reasons. The immutable rejection event should retain the observation, measurement time, and whether it was manually entered or read from a probe. The patch does not need to determine whether a probe is calibrated, but it should not erase provenance already supplied by the client.

### M3. Logs contain more location detail than troubleshooting requires

The planner’s completion log writes the driver’s raw latitude and longitude, every rejected candidate address, and the manifest ID in one structured record. This is convenient locally but broadens access to movement and recipient-location data through general application logs.

Log the relay search ID, rounded travel distance, reason-code counts, chosen recipient ID, and timing components. Exact coordinates should remain in the operational store with its narrower access policy. Candidate addresses are unnecessary because stable IDs allow an authorized investigator to retrieve them. Please also remove the food description from the error message emitted on travel-provider timeout; a lot ID and handling class are enough to diagnose that path.

## Tests and maintainability

The unit tests are readable and use a fixed clock consistently. The table-driven eligibility cases are especially useful, and the migration test proves that a relay leg cannot refer to itself as its parent. The code also keeps provider-specific route responses out of the domain layer.

Before merge, I would require these additions:

1. completion-time boundary tests described in B1;
2. outbox crash and duplicate-delivery tests;
3. two-transaction reservation contention and idempotent release tests;
4. simultaneous duplicate rejection requests against PostgreSQL;
5. a zero-degree temperature observation test;
6. a query-count test that demonstrates candidate count does not multiply SQL round trips; and
7. a property test asserting that increasing journey or service duration can never turn an ineligible candidate into an eligible one.

One existing test should be changed rather than extended. `test_fastest_candidate_always_wins` encodes a rule the production scorer does not actually promise. Rename it around the specific weighted components and assert the score breakdown. Otherwise a valid policy-weight change will look like a routing regression.

## Migration and rollout

The migration is additive and can be deployed before application code. However, the branch enables relay planning for all rejection reasons as soon as the worker starts. I recommend a staged switch keyed by depot or service area:

1. deploy schema, outbox worker, and metrics with relay creation disabled;
2. enable shadow planning, persisting candidate decisions without reserving food or notifying drivers;
3. compare predicted plans with dispatcher choices for a limited set of depots;
4. enable live assignment for one depot with an immediate kill switch; and
5. expand only after reservation conflicts, second-rejection rate, and deadline slack are visible.

At minimum, instrument search latency, candidate counts, reason-code counts, planned completion slack, outbox age, reservation conflicts, notification retries, driver acceptance, and second-handoff rejection. Alert on old undelivered outbox rows and assignments whose planned completion passes without a terminal custody event.

Rollback must stop new searches without deleting reservation or custody records. Disabling the feature should leave existing assignments visible and releasable; otherwise a rollback during an incident could strand quantities in the new balance table.

## Final decision

**Request changes** for B1, B2, H1, and H2. They affect deadline correctness, delivery of assignments, inventory integrity, and retry safety—the core guarantees of this workflow. H3 should be resolved before broad rollout, though it could be addressed through a conservative minimum-slack configuration if the scoring model needs separate product review.

The underlying design is worth continuing. Immutable custody events, explainable eligibility, integer quantities, and an explicit recovery path provide a sound base. Once completion-time feasibility, transactional publication, and reservation idempotency are in place, the relay flow should be suitable for a controlled depot-level trial.
